# Security Architecture

Документ описывает модель угроз, защитные контроли и архитектуру безопасности платформы. Используется для проектирования, security review, ИБ-аудитов в банках, подготовки к сертификациям.

---

## 1. Принципы безопасности

- **Defense in depth.** Никогда не полагаемся на один уровень защиты
- **Least privilege.** Минимально необходимые права у любого субъекта
- **Zero trust between services.** mTLS между сервисами, явная авторизация на каждом запросе
- **Secure by default.** Дефолтные конфигурации — самые строгие. Расслабление — через осознанное решение и аудит-запись
- **Audit everything.** Любое значимое действие — событие в audit log с подписью
- **Crypto в основе, не как опция.** Шифрование данных в покое и в транзите — всегда, а не «по запросу банка»
- **Мы не доверяем сами себе.** Наши сотрудники не должны иметь доступа к ПДн клиентов; доступ только при инциденте, через break-glass с уведомлением банка

## 2. Threat Model (STRIDE)

Применяем STRIDE-фреймворк к ключевым активам.

### 2.1 Активы

| Актив | Критичность | Где живёт |
|---|---|---|
| ПДн клиентов (паспорта, ИНН, адреса) | **Высшая** | PostgreSQL + S3 |
| Документы клиентов (уставы, протоколы) | **Высокая** | S3/MinIO |
| УКЭП-подписи и сертификаты | **Высшая** | Vault Transit + КриптоПро |
| Audit log | **Высшая** | Append-only PostgreSQL |
| Учётные записи операторов банка | **Высокая** | Keycloak |
| Конфигурации тенантов | **Средняя** | Git + Vault для секретов |
| Веса LLM | **Средняя** | Object storage |
| Промпты | **Средняя** | Git |
| Метрики и логи | **Низкая** | Prometheus, Loki |

### 2.2 Угрозы по STRIDE

| Угроза | Сценарий | Контроль |
|---|---|---|
| **S**poofing | Атакующий выдаёт себя за оператора банка | mTLS + сильная аутентификация (УКЭП или MFA для персонала); проверка JWT на каждом запросе |
| **S**poofing | Атакующий выдаёт себя за клиента | ЕСИА + УКЭП в основном сценарии; биометрия как опция |
| **T**ampering | Изменение audit log | Подпись каждой записи + цепочка hash-ей; immutable storage |
| **T**ampering | Изменение документа после подписания | Хеш документа в момент подписания + проверка перед использованием |
| **R**epudiation | Клиент отрицает, что подавал заявку | УКЭП с проверкой на стороне банка; полный audit trail с IP, временем, hash-ами |
| **R**epudiation | Сотрудник банка отрицает решение | Audit log с подписью; не может быть удалён |
| **I**nformation disclosure | Утечка БД с ПДн | Шифрование в покое; раздельные ключи на тенант; access logging |
| **I**nformation disclosure | Cross-tenant утечка | Schema-per-tenant; запросы фильтруются на уровне ORM; pen-test scenarios |
| **I**nformation disclosure | Логи содержат ПДн | PII-фильтр перед записью в логи; явный allow-list полей |
| **I**nformation disclosure | LLM запоминает данные клиента | PII-фильтр перед отправкой в модель; запрет fine-tuning на production-данных |
| **D**enial of service | Перегрузка одним тенантом | Rate limiting per-tenant; resource quotas |
| **D**enial of service | LLM-запросы съедают всю GPU | Per-tenant и per-user квоты в LLM Gateway |
| **D**enial of service | Атака на ext-API (ЕГРЮЛ) | Кэширование + circuit breakers |
| **E**levation of privilege | Compromise сервиса даёт доступ к другим | mTLS + service identities; не доверяем service-to-service без явной auth |
| **E**levation of privilege | Compromise admin-панели | MFA + IP-allowlist + аудит всех действий админа |

### 2.3 Особо чувствительные сценарии

**Сценарий «инсайдерская утечка»**:

- Сотрудник наш или банка-клиента имеет доступ к продакшен-данным
- Контроли: разделение duties, MFA, логирование всех доступов, регулярный review логов

**Сценарий «компрометация LLM-провайдера» (если SaaS-режим с внешним API)**:

- В этом случае паспорта клиентов могут оказаться в логах модели
- Контроль: при использовании внешних API (только если банк явно разрешил) — обязательный PII-фильтр перед отправкой; для on-prem — модели в периметре, проблема не возникает

**Сценарий «атака на цепочку поставок»**:

- Заражение npm-пакета или Docker-образа, который мы используем
- Контроли: SBOM (Software Bill of Materials) для каждого релиза; container scanning (Trivy); pinned versions; внутренний proxy для зависимостей

## 3. Identity & Access Management

### 3.1 Идентификация субъектов

Различаем пять типов субъектов и их способы аутентификации:

| Субъект | Способ аутентификации | MFA |
|---|---|---|
| Конечный клиент (юрлицо) | ЕСИА / УКЭП / логин+пароль+SMS | Обязательно для критичных действий |
| Сотрудник банка-клиента (оператор/комплаенс) | Keycloak SSO + MFA (TOTP/HW-токен) | Всегда |
| Наш сотрудник (поддержка) | Корпоративный SSO + HW-токен | Всегда + just-in-time доступ |
| Внутренний сервис | mTLS-сертификат + service account JWT | N/A |
| Внешний сервис (АБС, ЕГРЮЛ) | mTLS / API-ключи в Vault | N/A |

### 3.2 Авторизация (RBAC + ABAC)

- Role-based access control как база
- Attribute-based для тонких случаев (например, доступ к конкретной заявке только если оператор работает с её риск-категорией)
- Все роли и политики — в Keycloak с регулярным аудит-экспортом

**Ключевые роли:**

- `client.applicant` — конечный клиент (доступ только к своей заявке)
- `bank.operator` — оператор первой линии (создание, базовые проверки)
- `bank.compliance_officer` — комплаенс-офицер (решения по средним и высоким рискам)
- `bank.admin` — админ банка-тенанта (конфигурация, отчёты)
- `platform.support_engineer` — наш инженер поддержки (только break-glass с уведомлением)
- `platform.admin` — наш админ (управление тенантами, без доступа к данным клиентов)

### 3.3 Break-glass процедура

Для критичных инцидентов нашему инженеру нужен прямой доступ к данным банка:

1. Запрос на break-glass с обоснованием
2. Аппрув от security-офицера + уведомление CISO банка
3. Time-limited access (макс 4 часа)
4. Полная видеозапись сессии
5. Post-mortem обязательно
6. Audit-запись хранится отдельно, неудаляемо

## 4. Network Security

### 4.1 Сегментация

```
┌─────────────────────────────────┐
│ Internet                         │
└────────────┬────────────────────┘
             │
        ┌────▼────┐
        │   WAF   │ (Cloudflare / собственный)
        └────┬────┘
             │
        ┌────▼─────┐
        │ Ingress  │ (nginx + cert-manager)
        └────┬─────┘
             │
   ┌─────────▼──────────┐
   │ Public-facing zone │  (BFF, API Gateway)
   └─────────┬──────────┘
             │ (mTLS)
   ┌─────────▼──────────┐
   │  Internal zone     │  (Core services, AI agents)
   └─────────┬──────────┘
             │ (mTLS)
   ┌─────────▼──────────┐
   │  Data zone         │  (PostgreSQL, Kafka, Redis)
   └─────────┬──────────┘
             │
   ┌─────────▼──────────┐
   │  Adapter zone      │  (ABS adapters → банковский АБС)
   └────────────────────┘
```

- Между зонами — Network Policies в Kubernetes
- Service mesh (Istio) обеспечивает mTLS и authz
- Adapter zone имеет отдельный outbound к АБС — никаких других connections

### 4.2 Внешние подключения

- **Outbound разрешён только к white-list endpoints** (ЕГРЮЛ, ЕСИА, Росфинмон, банковский АБС)
- **Все outbound через корпоративный proxy** с логированием
- **DNS-блокировка** для подозрительных доменов

### 4.3 Защита от DDoS

- На уровне cloud-провайдера (Yandex DDoS Protection / VK Cloud)
- WAF с правилами OWASP top-10
- Per-tenant rate limiting в API Gateway
- Costly endpoints (документы, OCR) — дополнительные лимиты

## 5. Data Security

### 5.1 At-rest шифрование

| Слой | Механизм |
|---|---|
| Volume-level | LUKS для on-prem, native encryption в облаках |
| PostgreSQL | TDE (Transparent Data Encryption) |
| Object storage | Server-side encryption с управляемыми ключами |
| Backups | Шифрование перед загрузкой в storage |
| Kafka topics | Encryption at rest (KIP-405) |

**Ключи:** в Vault или банковском HSM. Ротация раз в год для master-keys, при необходимости — оперативно.

### 5.2 Field-level шифрование чувствительных данных

Особо чувствительные поля шифруются на уровне приложения, дополнительно к TDE:

- Серия и номер паспорта
- ИНН физлица
- СНИЛС
- Полные паспортные данные

Используется Vault Transit. В случае компрометации БД эти поля останутся зашифрованными.

### 5.3 In-transit шифрование

- **TLS 1.3** для всех публичных endpoints
- **mTLS** для service-to-service
- **TLS 1.2+** для внешних API (некоторые legacy АБС поддерживают только до 1.2)
- Шифрование сертификатами по алгоритмам RSA-3072 / ECDSA-P-256, для ГОСТ-режима — ГОСТ-2012

### 5.4 In-use защита

- LLM не получает chunks данных, в которых не нуждается
- Перед отправкой в LLM — PII-маскирование там, где сами поля не нужны для задачи
- Confidential computing для критичных операций — пока не закладываем (дорого), но архитектурно совместимо

## 6. Криптография

### 6.1 Стек

| Назначение | Алгоритмы | Реализация |
|---|---|---|
| TLS веб-трафик | RSA-3072, ECDSA-P-256 | OpenSSL / BoringSSL |
| TLS для УКЭП-режима | ГОСТ Р 34.10-2012 | КриптоПро CSP |
| Подпись документов УКЭП | ГОСТ Р 34.10-2012 | КриптоПро / VipNet |
| Хеш для audit log | SHA-3-256 | Native Go/Python |
| Symmetric encryption (БД, объекты) | AES-256-GCM | Vault Transit |
| Hash паролей | Argon2id | Native |
| JWT signing | EdDSA (Ed25519) | Native |

### 6.2 Key Management

- **Vault** как центральный KMS (HA-режим)
- Иерархия ключей: master-key (HSM или sealed Vault) → tenant-keys → data-keys
- Ротация ключей: master — раз в год; tenant — раз в 2 года; data — при компрометации
- Backup ключей в офлайн-хранилище (3-2-1 правило)

### 6.3 Особенности УКЭП

- **КриптоПро CSP** — основной СКЗИ-провайдер (наибольшая поддержка в РФ)
- **VipNet CSP** — альтернатива для банков, использующих VipNet
- Использовать только сертифицированные сборки СКЗИ
- Лицензия на СКЗИ — у банка-клиента; мы интегрируемся через стандартный API

## 7. Application Security

### 7.1 Secure Development Lifecycle

| Стадия | Контроли |
|---|---|
| Design | Threat modeling для новых фич; security review больших ADR |
| Develop | Pre-commit hooks (secrets detection); secure coding guidelines |
| Build | SBOM generation; dependency scanning (Snyk/Trivy) |
| Test | SAST (Semgrep); DAST на staging; контракт-тесты с security-кейсами |
| Deploy | Image signing; admission controllers в K8s; pinned image digests |
| Run | Runtime monitoring (Falco); anomaly detection в логах |
| Respond | Incident response runbook; quarterly DR drills |

### 7.2 OWASP Top 10 — типовые контроли

| OWASP | Контроль |
|---|---|
| A01 Broken Access Control | RBAC в Keycloak + проверки на каждом эндпоинте; интеграционные тесты |
| A02 Cryptographic Failures | См. раздел 6 |
| A03 Injection | ORM везде; sqlc для типизированных запросов; input validation на BFF |
| A04 Insecure Design | Threat modeling в design-стадии; security review |
| A05 Security Misconfiguration | Hardened defaults; конфигурация в Git; admission policies |
| A06 Vulnerable Components | Dependency scanning еженедельно; пакеты только из allowed registries |
| A07 Identification & Authentication | См. раздел 3 |
| A08 Software & Data Integrity | Image signing; SBOM; immutable infrastructure |
| A09 Logging & Monitoring | См. раздел 8 |
| A10 SSRF | Whitelist outbound; нет подключений к произвольным URL |

### 7.3 Секреты

- Никогда в Git
- Никогда в логах (отдельный фильтр)
- Никогда в env-переменных production-сервисов (используем Vault sidecar или CSI)
- Ротация при компрометации в течение 1 часа
- При увольнении сотрудника с доступом — ротация всех его секретов в течение 24 часов

## 8. Logging, Monitoring, Audit

### 8.1 Уровни логирования

| Уровень | Что | Где живёт | Срок хранения |
|---|---|---|---|
| Application logs | Поток выполнения, ошибки | Loki | 1 год |
| Access logs | Кто что запрашивал | Loki + audit DB | 3 года |
| Audit log | Доменные события (решения, подписи) | PostgreSQL append-only | 5 лет |
| Security events | Подозрительные действия | SIEM | 3 года |
| LLM call logs | Каждый вызов модели | PostgreSQL | 5 лет |

### 8.2 Что обязательно логируется

- Все аутентификации (успехи и провалы)
- Все изменения прав доступа
- Все обращения к ПДн (read-events)
- Все решения по заявкам (включая ИИ-рекомендации)
- Все экспорты данных
- Все break-glass-доступы
- Все админ-действия
- Все криптографические операции (подписи, шифрования)
- Все вызовы LLM (промпт + ответ)

### 8.3 Что НЕ должно попадать в логи

- Пароли и токены (даже одноразовые)
- Полные ПДн (паспортные данные — только masked)
- Контент медицинских / иных особо чувствительных данных (если попадут)
- API-ключи внешних сервисов

PII-фильтр на стороне приложения + дополнительная фильтрация на уровне log shipper.

### 8.4 Мониторинг и алерты

Алерты в трёх категориях с разными SLA:

- **P0 (15 мин)**: компрометация (множественные failed logins, аномалии в audit log, подозрительный outbound traffic)
- **P1 (1 час)**: операционные проблемы безопасности (просроченные сертификаты, упавший Vault, ошибки шифрования)
- **P2 (1 день)**: гигиена (устаревшие зависимости, security findings из сканеров)

## 9. Инцидент-менеджмент

### 9.1 Категории инцидентов

| Категория | Примеры | SLA уведомления |
|---|---|---|
| **Critical** | Утечка ПДн; компрометация ключей; неавторизованный доступ к продакшену | 1 час банку, 24 часа РКН |
| **High** | Подозрение на инцидент; неудачные атаки с обходом одного слоя защиты | 4 часа банку |
| **Medium** | Уязвимость без эксплуатации; некорректная конфигурация | 1 рабочий день банку |
| **Low** | Гигиенические находки | Еженедельный отчёт |

### 9.2 Процесс реагирования

1. **Detect** — мониторинг, отчёты пользователей, внешние уведомления (CERT)
2. **Triage** — security-офицер на дежурстве оценивает категорию
3. **Contain** — изоляция (например, отзыв ключа, блокировка IP, остановка сервиса)
4. **Investigate** — log analysis, forensics
5. **Remediate** — устранение root cause
6. **Notify** — уведомление банка-клиента, при необходимости — РКН (24 часа на 152-ФЗ-инциденты)
7. **Post-mortem** — обязательный для P0 и P1, с публикацией в команде

### 9.3 DR (Disaster Recovery)

- RPO 15 минут (потеря данных не более 15 минут)
- RTO 4 часа (восстановление работы за 4 часа)
- Backup стратегия: ежедневные полные + continuous WAL для PostgreSQL
- Cold-site в другом регионе
- Quarterly DR drills с реальным failover
