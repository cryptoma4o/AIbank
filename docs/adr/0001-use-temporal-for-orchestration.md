# ADR-0001: Использование Temporal для оркестрации онбординг-воркфлоу

**Status:** Accepted  
**Date:** 2026-04-26  
**Authors:** Главный архитектор  
**Reviewers:** Тех-лид backend, Security-инженер

## Context

Онбординг юрлица — это длинный мульти-шаговый процесс, занимающий от минут (для ИП) до нескольких дней (для АО). Процесс включает:

- Параллельные операции (загрузка документов одновременно с запросом в ЕГРЮЛ)
- Длинные ожидания (запрос документов у клиента — может занять до 14 дней)
- Внешние интеграции с непредсказуемой задержкой (АБС, ЕГРЮЛ, ЕСИА)
- Транзакционная семантика (открытие счёта в АБС — это цепочка операций, требующая компенсаций при сбоях)
- Возможность ручного вмешательства (комплаенс-офицер может приостановить или направить заявку на доработку)
- Требование полного audit trail (115-ФЗ — 5 лет хранения)

Без специализированной системы это потребует:

- Самописного state machine для каждой ветки воркфлоу
- Собственного механизма retry с backoff
- Решения для compensating actions (SAGA)
- Хранилища состояний воркфлоу с восстановлением после сбоев
- Логирования всех переходов

Это значительный объём «инфраструктурной» работы, которая не относится к нашему value proposition. И исторически такие самописные решения сложно поддерживать через 2-3 года.

## Decision

Используем **Temporal** как движок оркестрации онбординг-воркфлоу.

- Каждый Application = один Temporal Workflow
- Активности (вызовы внешних сервисов, ИИ-агентов, АБС-операций) — Temporal Activities
- Длинные ожидания клиента реализуются через Temporal `await` без блокирования рабочих потоков
- SAGA-паттерны строим на Temporal compensations
- Исторические данные о выполнении воркфлоу служат частью audit log

Развёртывание: self-hosted Temporal Cluster (PostgreSQL backend, никаких managed-сервисов чтобы поддерживать on-prem).

## Alternatives Considered

### Альтернатива 1: Самописный state machine + Kafka для событий

**Плюсы:**
- Нет внешней зависимости
- Полный контроль над логикой

**Минусы:**
- 6-12 месяцев инженерного времени на нетривиальный, но базовый функционал
- Высокая сложность тестирования (особенно failure-сценарии)
- Самостоятельное решение проблем deduplication, ordering, replay
- Высокий риск ошибок в реализации SAGA-семантики

**Причина отклонения:** не наш value-проп; лучше потратить эти 6-12 месяцев на ИИ-агентов и UX.

### Альтернатива 2: AWS Step Functions / Yandex Cloud Workflows

**Плюсы:**
- Managed-решение, не надо администрировать
- Встроенные интеграции с другими сервисами облака

**Минусы:**
- Vendor lock-in
- **Не поддерживает on-prem** — критическое ограничение для банков
- Лимиты на длительность воркфлоу (для AWS — 1 год максимум)
- Сложно дебажить

**Причина отклонения:** несовместимо с гибридной моделью развёртывания.

### Альтернатива 3: Apache Airflow

**Плюсы:**
- Распространён, много специалистов
- Open-source

**Минусы:**
- Ориентирован на batch-задачи (DAG-и для ETL), не на long-running event-driven процессы
- DAG-семантика не очень хорошо ложится на наш сценарий
- Нет встроенных SAGA-паттернов
- Слабая поддержка ожиданий внешних событий

**Причина отклонения:** парадигма не подходит — Airflow для пайплайнов данных, не для бизнес-процессов.

### Альтернатива 4: Camunda

**Плюсы:**
- Зрелая система оркестрации
- BPMN-подход — понятен бизнес-аналитикам банка
- Поддержка SAGA

**Минусы:**
- Java-стек (наш основной язык — Go)
- BPMN-визуализация хороша, но избыточна для нашего сценария
- Лицензирование enterprise-фич — дополнительные расходы
- Тяжелее в эксплуатации, чем Temporal

**Причина отклонения:** для нашей модели (не нужна BPMN-визуализация) — overkill; Temporal проще и легче.

## Consequences

### Positive

- Существенно сокращаем время до MVP (по нашей оценке, экономим 6+ месяцев)
- Получаем zoom-in видимость каждого выполнения воркфлоу через Temporal UI
- Лёгкое тестирование time-зависимых сценариев (Temporal позволяет «двигать время» в тестах)
- Встроенный visibility для комплаенс-офицеров (через Temporal UI с ограниченным доступом)
- Стандартные паттерны для retry, timeout, compensation
- Гибкость: при необходимости заменить технологию — workflow-логика отделена от инфраструктуры

### Negative

- Дополнительная инфраструктурная зависимость, которую нужно администрировать
- Команде нужно изучить Temporal-парадигму (Workflow Functions, Activities, Signals)
- Temporal-cluster требует PostgreSQL/Cassandra — дополнительные ресурсы
- Ограничение Go SDK: некоторые продвинутые фичи появляются позже, чем в Java SDK
- При сбое Temporal — все онбординги встают (mitigation: HA-deployment Temporal-кластера)

### Neutral

- Версионирование воркфлоу-кода — есть встроенная поддержка, но требует дисциплины
- Глобальный лимит на размер payload активностей — нужно следить, чтобы не передавать большие документы напрямую (используем ID + загрузку из object storage)

## Implementation Notes

- На старте Temporal-кластер один на платформу (multi-tenant через namespaces)
- В перспективе — отдельный Temporal Cluster на банк-тенанта в on-prem развёртываниях
- Доступ к Temporal UI — через Keycloak SSO с RBAC
- Backup схемы Temporal — каждый час, retention 30 дней
- Для каждого Workflow type — обязательное наличие e2e-теста с использованием Temporal Test Framework
