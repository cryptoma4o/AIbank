# Architecture Decision Records

Этот раздел содержит все архитектурные решения проекта. ADR — короткие документы (1-3 страницы), фиксирующие значимые решения и их обоснования.

## Когда писать ADR

Пишите ADR, когда решение:

- **Сложно отменить** (выбор языка, базы данных, фреймворка)
- **Влияет на несколько команд** или архитектурных слоёв
- **Имеет долгосрочные последствия** (security-стратегия, схема изоляции тенантов)
- **Требует обоснования** для новых членов команды
- **Может вызвать вопрос «почему так?»** через год

**НЕ пишите ADR** для:

- Тактических решений уровня одной задачи
- Фиксации факта (это документация, не решение)
- Решений, которые легко изменить (выбор UI-библиотеки внутри одного компонента)

## Принципы хороших ADR

- **Короткие.** 1-3 страницы. Если дольше — скорее всего, есть подзадачи для отдельных ADR
- **Фокус на «почему», а не на «как».** Имплементация может измениться, обоснование — нет
- **Без жаргона по возможности.** Через год новый член команды должен понять без отдельных пояснений
- **Не редактируем после accepted.** Если решение меняется — пишем новый ADR со статусом superseded
- **Date matters.** Контекст со временем меняется; зафиксированная дата помогает понять, актуально ли решение
- **Конкретные имена ответственных.** Не «команда», а имена

## Как создать новый ADR

1. Скопируйте `0000-template.md` в `NNNN-краткое-название.md`, где `NNNN` — следующий номер
2. Заполните по шаблону
3. Откройте PR с `Status: Proposed`
4. После обсуждения и аппрува минимум двух ревьюверов меняйте статус на `Accepted`
5. Добавьте запись в таблицу ниже

## Соглашения

- Нумерация — четырёхзначная, последовательная, без пробелов
- Имя файла — `NNNN-kebab-case-short-title.md`
- Не удаляем устаревшие ADR — помечаем `Status: Superseded by ADR-NNNN`
