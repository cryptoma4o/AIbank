# ADR-0002: Schema-per-tenant в PostgreSQL для изоляции данных банков

**Status:** Accepted  
**Date:** 2026-04-26  
**Authors:** Главный архитектор  
**Reviewers:** Тех-лид backend, Security-инженер, DBA

## Context

Платформа multi-tenant по требованию (см. `docs/technical-structure.md` § 1, принцип №1): каждый банк — изолированный тенант, никаких `tenant_id` в общих таблицах. На уровне реализации это означает один из трёх подходов к организации хранения в PostgreSQL.

Силы, давящие на это решение:

- **Регуляторика.** 152-ФЗ требует, чтобы ПДн клиентов одного банка были технически отделены от ПДн другого. УЗ-2 в части аттестации требует обоснования механизма изоляции.
- **Банковский ИБ-аудит.** При внедрении в каждом банке проводится отдельный аудит. «Все банки в одной таблице с фильтром по `tenant_id`» — позиция, которую невозможно защитить перед банковским CISO.
- **Hybrid deployment.** Тот же артефакт работает в SaaS (10–30 тенантов на кластер) и в on-prem (один тенант — сам банк, разворачивает в своём контуре). Решение должно одинаково работать в обоих режимах.
- **Размер тенанта.** Банк ЦА — 5–50 тыс. открытых счетов в год. По доменной модели на одну заявку: ~1 Application + ~10 Document + ~3 Person + 1–2 RiskAssessment + ~50 AuditEvent. Через 3 года в активном тенанте — 0.5–5 млн заявок и 25–250 млн audit-событий.
- **Per-tenant операции.** Backup, restore, экспорт, удаление по запросу клиента (ст. 14 152-ФЗ), миграция в on-prem из SaaS, пересмотр ключей шифрования — должны выполняться на одном тенанте без затрагивания остальных.
- **Бюджет инфраструктуры.** Целевая юнит-экономика — 17.5 млн руб./год с банка (см. product-vision.md § 5). Расходы на отдельный managed-Postgres-кластер на тенанта (10–30 тыс. руб./мес. × 12 = 120–360 тыс./год + админ-затраты) для 30 тенантов — это уже 3.6–10.8 млн руб./год, заметная доля маржи.
- **Cross-tenant операции платформы.** Биллинг агрегирует события по всем банкам, ops-dashboard сводит метрики, audit-репорты для нашего комплаенса — нужны без хождения по 30 разным БД.

Если ничего не решить, разные сервисы примут несовместимые решения (часть с `tenant_id`, часть с отдельными схемами), и расхождение придётся переписывать на этапе первого банковского аудита.

## Decision

Используем **schema-per-tenant** в одном PostgreSQL-кластере как основной паттерн изоляции данных тенантов.

- Каждый тенант = отдельная PostgreSQL **schema** (`tnt_<short_id>`), все доменные таблицы создаются в схеме тенанта.
- **Один кластер PostgreSQL** обслуживает множество тенантов в SaaS-режиме; в on-prem-развёртывании в кластере физически один тенант, но логически структура та же.
- **Соединение и `search_path`** — каждое подключение от сервиса к БД устанавливает `SET search_path TO tnt_<id>` на основе извлечённого из JWT/контекста `tenant_id`. Запросы пишутся без префикса схемы.
- **`tenant-service` — единственный владелец метаданных тенантов.** Реестр тенантов (соответствие `tenant_id` ↔ имя схемы, статус, deployment_mode, ссылки на конфиги в Vault) хранится в **отдельной служебной схеме `platform`** того же кластера.
- **Cross-tenant сервисы** (`billing-service`, `audit-service` для платформенной отчётности, `ops-dashboard`) подключаются к схеме `platform` и получают агрегаты через **витрины с `SECURITY DEFINER`-функциями** или через события Kafka, а не через прямые `JOIN` между схемами тенантов.
- **DDL-миграции** применяются к каждой схеме тенанта последовательно через `tenant-service` (см. ADR-0005, который примет конкретный механизм). На один merge в `main` — один и тот же набор миграций прогоняется по всем активным тенантам в строго определённом порядке.
- **Database-per-tenant как escape hatch.** Архитектурно сохраняем абстракцию `TenantConnection`, которая в SaaS возвращает `(shared_cluster, schema=tnt_xyz)`, а в on-prem или для тенанта с особыми требованиями — `(dedicated_cluster, schema=public)`. Точка переключения — конфигурация тенанта, не код приложения.
- **Что НЕ перекрывает это решение:**
  - Объектное хранилище (отдельный bucket на тенанта в MinIO/S3) — другое ADR не требуется, паттерн уже зафиксирован.
  - Kafka-топики (префикс `tnt.<id>.<topic>`) — фиксируется в инфраструктурных конфигурациях.
  - LLM Gateway namespaces — отдельный namespace с per-tenant rate-limit, см. `docs/security-architecture.md` § 5.

## Alternatives Considered

### Альтернатива 1: Database-per-tenant (отдельная БД на банк)

**Плюсы:**
- Максимальная изоляция: разные `pg_hba.conf`, разные роли, разные backups, разные WAL.
- Самая простая позиция перед банковским ИБ-аудитом — «у вашего банка отдельная база».
- Per-tenant ресурсные лимиты на уровне ОС.
- Простой `pg_dump`/`pg_restore` по тенанту.
- Естественно ложится на on-prem (там это всё равно так).

**Минусы:**
- В SaaS-режиме на 30 тенантов — 30 отдельных БД с собственными connection pools (PgBouncer становится нетривиальной конструкцией).
- Cross-tenant запросы (биллинг, платформенная аналитика) требуют отдельного pipeline через CDC или Kafka — лишний слой сложности с самого начала.
- Стоимость инфраструктуры в SaaS — описана в Context, существенно бьёт по марже.
- Миграции — оркестрация по N кластерам с retry/rollback — самостоятельный поджанр сложности.
- Connection-pool exhaustion: каждый сервис умножает (число реплик) × (число тенантов) подключений к разным БД.

**Причина отклонения:** избыточно для SaaS-режима с банками среднего размера; уровень изоляции, который даёт `database-per-tenant` сверх `schema-per-tenant`, на практике достигается комбинацией ролей PostgreSQL, `search_path`, ORM-фильтра и отдельных KMS-ключей шифрования (см. § 5 security-architecture). Для on-prem схема всё равно сводится к database-per-tenant тривиально (там тенант один). Сохраняем как escape hatch, но не используем по умолчанию.

### Альтернатива 2: Shared schema с дискриминатором `tenant_id`

**Плюсы:**
- Самая дешёвая инфраструктура (один кластер, одни таблицы).
- Простейшие миграции (один `ALTER TABLE` на всех).
- Удобные cross-tenant запросы.
- Подход хорошо изучен (Salesforce, Atlassian Cloud).

**Минусы:**
- **Прямо нарушает зафиксированный архитектурный принцип** «никаких `tenant_id` в общих таблицах» (`docs/technical-structure.md` § 1).
- Каждая ошибка в коде — потенциальный cross-tenant data leak. Один забытый `WHERE tenant_id = $1` = инцидент уровня P0 с уведомлением РКН.
- Невозможно защитить перед банковским ИБ-аудитом без героических усилий (RLS + множественные роли + раздельные ключи на уровне поля). Это и есть схема в схему, только ещё хрупче.
- Per-tenant backup/restore — нужно писать самим через фильтр.
- Удаление тенанта (или его данных по 152-ФЗ) — DELETE по огромным таблицам с долгим VACUUM.
- Нет естественной точки приложения per-tenant ресурсных лимитов.

**Причина отклонения:** противоречит уже принятому архитектурному принципу; риски security-инцидентов из-за человеческих ошибок несоразмерно выше выигрыша в простоте.

### Альтернатива 3: Schema-per-tenant + PostgreSQL Row-Level Security как «пояс и подтяжки»

**Плюсы:**
- К schema-per-tenant добавляется RLS-policy, требующая `current_setting('app.tenant_id') = 'X'`. Вторая линия защиты от ошибки в `search_path`.

**Минусы:**
- Дублирует контроль и усложняет ORM/sqlc-генерацию (sqlc не очень дружит с RLS-контекстом).
- Performance-overhead RLS на горячих запросах нетривиален.
- Сложнее отлаживать «почему запрос вернул 0 строк».

**Причина отклонения:** оставляем как опцию для будущего, если по результатам pen-test или инцидента появится конкретное обоснование. Сейчас — over-engineering.

### Альтернатива 4: Sharding по `tenant_id` на уровне Citus / pgvector-подобных расширений

**Плюсы:**
- Горизонтальное масштабирование «из коробки».

**Минусы:**
- Требование hybrid deployment запрещает managed-сервисы и редкие расширения. Citus в on-prem — отдельный продукт со своим жизненным циклом.
- Нам не нужно горизонтальное масштабирование на старте: 30 тенантов × 5 млн записей в активной таблице — это легко влезает в один well-tuned Postgres 16.

**Причина отклонения:** решение задачи, которой ещё нет. При росте до 100+ тенантов можно будет вернуться (тогда же, скорее всего, имеет смысл рассматривать database-per-tenant с шардированием на уровне приложения).

## Consequences

### Positive

- Принцип «никаких `tenant_id` в общих таблицах» соблюдается на уровне физической модели.
- Резервное копирование, восстановление, экспорт и удаление одного тенанта — стандартные операции PostgreSQL (`pg_dump --schema=tnt_xyz`).
- Один CI-pipeline, один artifact, одинаковая модель в SaaS и on-prem.
- Per-tenant ресурсные лимиты возможны через PostgreSQL-роли (`ALTER ROLE ... CONNECTION LIMIT`, `pg_stat_statements` на роль).
- ИБ-аудит в банке: показываем отдельную схему, отдельную роль с грантом только на эту схему, отдельный шифр-ключ Vault Transit для PII-полей — закрывает требования УЗ-2 на изоляцию.
- Cross-tenant операции (биллинг, audit-репорты для платформы) реализуются через явный, аудируемый интерфейс (`platform.*` + `SECURITY DEFINER`), а не неявно через `JOIN`.
- Миграция тенанта из SaaS в on-prem — `pg_dump` схемы → `pg_restore` в новый кластер. Без переписывания.

### Negative

- **Миграции дороже.** На каждый DDL-релиз нужно прогнать миграции по N схемам с обработкой частичных сбоев. Требует отдельной инфраструктуры (см. ADR-0005). Цена этой инфраструктуры — 1–2 месяца работы Backend + DBA.
- **Connection pool сложнее.** Сервис не может ленивым образом подключаться к произвольной схеме — нужна обвязка вокруг pgxpool/pgbouncer, которая выставляет `search_path` per-request или per-pool. Это не разовая работа, а долгоживущая абстракция в `packages/`.
- **Лимит на число тенантов в одном кластере.** По мере роста (>50–100 тенантов в SaaS) `pg_class` начнёт ощутимо распухать (десятки таблиц × N схем = тысячи таблиц), `pg_dump` всего кластера замедлится, `autovacuum` будет страдать. До этого порога — далеко, но решение придётся пересматривать.
- **Невозможно лениво писать запросы с `JOIN` между тенантами.** Это и есть фича, но в редких операционных задачах (ad-hoc-запрос аналитика к двум банкам) — потребуется явная конструкция через `platform`-витрины или временное переключение `search_path`.
- **Нагрузка на DBA выше, чем при `database-per-tenant`.** Один большой кластер с 30 схемами требует иной экспертизы и иного подхода к мониторингу `bloat`/`vacuum`/`statistics`.

### Neutral

- В коде сервисов имена таблиц пишутся **без префикса схемы**. Префикс — ответственность connection middleware. Code review должен ловить хардкод схем — добавляем lint-правило для sqlc.
- ORM-выбор — sqlc (Go) и SQLAlchemy (Python для AI-сервисов с БД-доступом) — оба совместимы с переменным `search_path`, но требуют явной обвязки. Документируется в `packages/` README сервисов.
- Тестирование: каждый интеграционный тест использует свою временную схему. Это уже принятый паттерн в Go-тестах с testcontainers, дополнительной работы не требует.

## Implementation Notes

**Layout кластера**

```
postgres-cluster (shared in SaaS, dedicated in on-prem)
├── database: aibank
│   ├── schema: platform              -- tenant registry, billing, ops
│   │   ├── tenants
│   │   ├── tenant_keys (refs to Vault)
│   │   ├── billing_events
│   │   └── audit_platform
│   ├── schema: temporal_visibility   -- managed by Temporal
│   ├── schema: tnt_alfa_bank
│   │   ├── applications
│   │   ├── persons
│   │   ├── legal_entities
│   │   ├── documents
│   │   └── audit_events
│   ├── schema: tnt_demo
│   │   └── ...
│   └── schema: tnt_<id>
└── roles
    ├── platform_owner       -- migrations, DDL
    ├── platform_app         -- access to platform schema
    ├── tnt_<id>_owner       -- migrations on tenant schema
    └── tnt_<id>_app         -- runtime access on tenant schema only
```

**Создание нового тенанта** (через `tools/tenant-cli`):

1. `CREATE SCHEMA tnt_<id>`
2. Применение всей актуальной цепочки миграций к новой схеме.
3. Создание ролей `tnt_<id>_owner` и `tnt_<id>_app` с грантами только на эту схему.
4. Запись в `platform.tenants` с `status = pending_validation`.
5. Smoke-тест соединения и базовых CRUD от имени `tnt_<id>_app`.
6. Перевод в `status = active`.

**Подключение из сервиса**

```go
// pseudocode — точная реализация в packages/db/tenant.go
conn, err := pool.Acquire(ctx)
defer conn.Release()
tenantID := tenant.FromContext(ctx)
schema := "tnt_" + tenantID
if _, err := conn.Exec(ctx, fmt.Sprintf("SET LOCAL search_path TO %s, public", pq.QuoteIdentifier(schema))); err != nil {
    return err
}
// дальше обычные запросы без префикса схемы
```

`SET LOCAL` ограничивает действие текущей транзакцией — соединение возвращается в пул в чистом состоянии.

**Безопасность**

- В коде категорически запрещено формировать имя схемы из чего-либо, кроме `platform.tenants` lookup. SQL-инъекция через имя схемы — отдельный класс уязвимостей; защита через явный whitelist + `pq.QuoteIdentifier`.
- Сервисный аккаунт никогда не использует `platform_owner`. Только `tnt_<id>_app`.
- Запрос cross-schema из сервиса = ошибка ревью. Только через явные витрины `platform.*`.

**Деление ответственности**

| Компонент | Что хранит |
|---|---|
| `platform` | Реестр тенантов, биллинг-события, платформенный audit, метаданные конфигов |
| `tnt_<id>` | Все доменные сущности этого банка (Application, Person, Document, Decision, AuditEvent…) |
| Object storage | Файлы документов, отдельный bucket на тенанта |
| Vault | Секреты, ключи шифрования полей, refs из `platform.tenant_keys` |

**Открытые подзадачи, выносимые в отдельные ADR**

- **ADR-0005**: конкретный механизм миграций (golang-migrate? sqlmig? собственный orchestrator на Temporal?), порядок применения, политика rollback при частичном сбое.
- **ADR-0009**: применение миграций в on-prem (где у нас нет прямого доступа и квартальный релизный цикл).
