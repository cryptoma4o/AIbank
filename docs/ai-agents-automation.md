# Автоматизация онбординга с ИИ-агентами

Документ описывает, **что именно** и **как** автоматизируют ИИ-агенты в платформе онбординга юрлиц, где проходят границы автономности, и как агенты связаны между собой через оркестратор.

Это дополнение к [технической структуре проекта](technical-structure.md), фокусированное на логике автоматизации.

---

## 1. Принципы автоматизации

Перед тем как описать сами агенты, нужно зафиксировать несколько принципов, которые определяют **что делать можно, а что нельзя**. Эти принципы не подлежат переопределению через тенант-конфигурацию — они архитектурные.

**Принцип 1. Никаких автономных отрицательных решений.**
ИИ может рекомендовать «отказать клиенту», «повысить риск-категорию», «запросить дополнительные документы», но финальное действие, которое влечёт юридические или финансовые последствия для клиента, всегда совершает человек. Это требование 115-ФЗ и здравого смысла: автоматический отказ без human review это и юридический риск, и репутационная катастрофа при ошибке.

**Принцип 2. Положительные решения автоматизируются — но только в зелёной зоне.**
Если все проверки пройдены, скор низкий, расхождений с ЕГРЮЛ нет, УБО прозрачные — счёт открывается без участия человека. Это, собственно, и есть смысл автоматизации. Граница «зелёной зоны» — конфигурация банка-тенанта.

**Принцип 3. Объяснимость — обязательна для каждого ИИ-решения.**
Любая рекомендация агента сопровождается списком фактов и весов, которые к ней привели. Это и для аудита ЦБ, и для комплаенс-офицера, который кликает «одобрить».

**Принцип 4. Stateless-агенты, stateful-оркестратор.**
Агенты не хранят состояние между вызовами. Всё состояние заявки живёт в Temporal-воркфлоу. Это даёт идемпотентность, возможность откатывать шаги и повторять воспроизводимо.

**Принцип 5. Каждое действие агента — событие в audit log.**
Вход, выход, версия модели, версия промпта, latency, стоимость в токенах. Хранение 5 лет.

**Принцип 6. Человеку нужно работать только с неоднозначным.**
Цель автоматизации — не «убрать комплаенс-офицера», а избавить его от рутины. Из 100 заявок в зелёной зоне он не должен видеть ни одной. Из 100 спорных — он видит все, с уже подготовленным контекстом.

## 2. Контур автоматизации: что автоматизируем, что нет

| Этап онбординга | Уровень автоматизации | Кто решает |
|---|---|---|
| Приём заявки и идентификация | Полная автомат. (ЕСИА/УКЭП) | Система |
| Извлечение данных из документов | Полная автомат. с confidence-scoring | Система + (если low confidence) человек |
| Сверка с ЕГРЮЛ/ЕГРИП | Полная автомат. | Система |
| Скрининг по перечням 115-ФЗ | Полная автомат. | Система |
| Построение графа УБО | Автомат. + запрос документов у клиента | Система + клиент |
| Риск-скоринг | Автомат. (CatBoost + LLM-объяснение) | Система |
| **Решение «одобрить» (зелёная зона)** | **Автомат. в рамках политики тенанта** | Система |
| **Решение «отказать» или «повысить риск»** | **Никогда не автомат.** | Комплаенс-офицер |
| Открытие счёта в АБС | Полная автомат. (после одобрения) | Система |
| Уведомление клиента | Полная автомат. | Система |
| Периодический пересмотр (КУС) | Автомат. триггер + ручной разбор | Система → человек |

«Зелёная зона» для автоматического одобрения — это **строгий AND**: низкий риск-скор + 0 расхождений с ЕГРЮЛ + 0 совпадений в перечнях + прозрачная структура УБО (для ООО) + резидент РФ + «чистый» ОКВЭД + нет open issues от других агентов. По нашему опыту, в эту зону попадает 60–75% заявок ИП и 35–50% заявок ООО — что и так даёт огромную экономию.

## 3. Архитектура оркестрации

Центральная роль — у `onboarding-orchestrator` (Temporal-воркфлоу). Агенты — это **activities** в терминах Temporal. Воркфлоу определяет последовательность, condition-логику и обработку ошибок; агенты — это «руки», которые выполняют конкретные задачи.

**Высокоуровневая последовательность для ООО:**

```
[Application Created]
        ↓
  [Identity Verified]  ← identity-service (ЕСИА/УКЭП)
        ↓
  [Documents Uploaded]
        ↓
  ╔═══════════════════════════════════════════╗
  ║  Параллельно:                             ║
  ║  - Document Intake Agent → JSON           ║
  ║  - ext-egrul → ЕГРЮЛ JSON                 ║
  ╚═══════════════════════════════════════════╝
        ↓
  [Reconciliation Agent] → расхождения / OK
        ↓
  ┌─ если расхождения: → Conversational Agent → клиент
  │       ↓
  └─ если OK: продолжаем
        ↓
  [UBO Tracing Agent] (для ООО/АО)
        ↓
  [Screening: ext-rosfinmon] (параллельно)
  [Screening: ext-fssp]
        ↓
  [Risk Scoring Agent] → скор + объяснение
        ↓
  ╔═══════════════════════════════════════════╗
  ║  Решение:                                 ║
  ║  if green_zone(scoring): auto-approve     ║
  ║  else: → human review queue               ║
  ╚═══════════════════════════════════════════╝
        ↓
  [Decision: Approved]
        ↓
  [ABS Connector: OpenAccount SAGA]
        ↓
  [Notify Client]
```

Каждый шаг — отдельная Temporal activity с ретраями, таймаутами и компенсациями. Если на шаге УБО что-то сломалось через 2 часа после запуска воркфлоу, Temporal автоматически возобновит с этого места, не повторяя предыдущие.

**Передача состояния между агентами** — через `ApplicationContext`, immutable-снапшот всего, что собрано на текущий момент:

```yaml
ApplicationContext:
  application_id: "app-uuid"
  tenant_id: "bank-alpha"
  legal_entity_type: "LLC"
  applicant: {...}
  legal_entity: 
    egrul_data: {...}              # из ЕГРЮЛ
    extracted_documents: {...}     # от Document Intake Agent
    reconciliation_result: {...}   # от Reconciliation Agent
    ubo_graph: {...}               # от UBO Tracing Agent
    screening: {...}               # от ext-rosfinmon
  risk_assessment: null            # пока не посчитан
  trace_id: "..."                  # для observability
```

Каждый агент получает контекст на вход, возвращает обновление поля. Никаких side-effects на другие поля.

## 4. Каталог ИИ-агентов

### 4.1 Document Intake Agent

**Назначение.** Извлекает структурированные данные из загруженных документов (паспорт, устав, решение/протокол о назначении ЕИО, выписка из реестра акционеров для АО, доверенности).

**Входы:**
```yaml
DocumentIntakeInput:
  document_id: "doc-uuid"
  document_type: "passport | charter | protocol | shareholders_registry | ..."
  files: [{ "url": "s3://...", "mime": "image/jpeg" }]
  expected_fields_hint: ["inn", "ogrn", "director_name", ...]   # подсказка
```

**Выход:**
```yaml
DocumentIntakeOutput:
  extracted: {
    "inn": { "value": "7701234567", "confidence": 0.98, "bbox": [x,y,w,h] },
    "ogrn": { "value": "1027700123456", "confidence": 0.95, "bbox": [...] },
    "director_full_name": { "value": "Иванов Иван Иванович", "confidence": 0.87, "bbox": [...] },
    ...
  }
  document_quality: {
    "is_scan_readable": true,
    "has_seal": true,
    "is_signed": true
  }
  unparseable_regions: [...]   # фрагменты, где модель не уверена
```

**Модель.** Gemma 4 26B-MoE (multimodal) — основной кандидат. Решающим фактором будет точность на сканах с печатями и плохого качества (eval-harness корпус `docs-parsing`).

**Тулы (function calling):**
- `validate_inn(inn: str) → bool` — проверка контрольной суммы
- `validate_ogrn(ogrn: str) → bool` — проверка контрольной суммы и числа знаков
- `lookup_okved_name(code: str) → str` — название ОКВЭД по коду
- `validate_passport_series(series: str, number: str) → bool`

**Промпт-структура** (упрощённо):

```
Ты — система извлечения данных из российских банковских документов.
Тип документа: {{document_type}}.
Извлеки следующие поля: {{expected_fields_hint}}.

Для каждого поля верни значение, confidence (0..1) и bounding box.
Если поле не найдено — confidence=0 и value=null.
Используй tool validate_inn для проверки ИНН перед возвратом.

Не интерпретируй и не нормализуй данные сверх минимального — 
для ФИО возвращай как написано в документе (с заглавных или нет).

Верни строгий JSON по схеме:
{{schema_json}}
```

**Гардрейлы:**
- JSON validity check — при невалидном JSON ретрай до 3 раз с уточнением
- Confidence threshold — поля с `confidence < 0.85` помечаются для ручной проверки оператором
- PII не уходит в логи модели (логируется только metadata: тип документа, latency, % confidence)
- Если документ — паспорт, и confidence по серии/номеру < 0.95 → автоматический запрос загрузить более качественный скан

**Метрики качества:**
- Field-level F1 по каждому полю
- JSON validity rate (% корректных JSON с первой попытки)
- p99 latency
- % документов, ушедших на ручную проверку

### 4.2 Reconciliation Agent

**Назначение.** Сверяет данные, извлечённые из документов, с данными ЕГРЮЛ/ЕГРИП. При расхождениях — формирует естественно-языковой вопрос клиенту.

**Зачем нужен ИИ, а не просто `if extracted.X != egrul.X`?** Потому что расхождения часто нетривиальны:

- В уставе «Общество с ограниченной ответственностью "Ромашка"», в ЕГРЮЛ — «ООО "Ромашка"» — это **не** расхождение
- В уставе адрес «г. Москва, ул. Тверская, д. 1», в ЕГРЮЛ «117500, г. Москва, Тверская улица, дом 1» — это **не** расхождение по сути
- В уставе директор «Иванов И.И.», в ЕГРЮЛ — «Петров П.П.» — это **критическое** расхождение, скорее всего нужен свежий протокол

LLM нормализует строки, понимает синонимы, видит контекст и решает, требуется ли действие.

**Входы:**
```yaml
ReconciliationInput:
  extracted_documents: { ... }  # от Document Intake Agent
  egrul_data: { ... }           # от ext-egrul
  document_dates: { 
    "charter_version": "2023-04-15", 
    "egrul_snapshot": "2026-04-26" 
  }
```

**Выход:**
```yaml
ReconciliationOutput:
  status: "match" | "minor_discrepancies" | "critical_discrepancies"
  discrepancies: [
    {
      "field": "director.full_name",
      "extracted_value": "Иванов И.И.",
      "egrul_value": "Петров П.П.",
      "severity": "critical",
      "explanation": "ФИО директора не совпадает. Возможно, в ЕГРЮЛ внесены свежие данные о смене ЕИО.",
      "suggested_action": "request_document",
      "client_question": "В вашем уставе указан директор Иванов И.И., но в ЕГРЮЛ — Петров П.П. Пожалуйста, загрузите актуальный протокол о назначении ЕИО."
    }
  ]
  blocking_for_onboarding: true
```

**Модель.** Gemma 4 31B (или Qwen 3.5 27B — выбор по eval). Reasoning важен: модель должна понимать, какие расхождения существенны.

**Тулы:**
- `is_legal_form_synonym(s1: str, s2: str) → bool` — для сравнения «ООО» / «Общество с ограниченной ответственностью»
- `normalize_address(addr: str) → AddressStruct` — структуризация адресов
- `compute_string_similarity(s1: str, s2: str) → float` — для имён собственных

**Severity-классификация** (запекаем в промпт + правила):

| Severity | Примеры | Действие |
|---|---|---|
| `informational` | Расхождение в форматировании адреса | Логируем, не блокируем |
| `minor` | Устаревший ОКВЭД | Запрос подтверждения у клиента |
| `critical` | Смена директора, изменение наименования | Запрос документа, блокируем продолжение |
| `red_flag` | ИНН/ОГРН не совпадают | Ручной разбор комплаенс-офицером, повышение риска |

**Гардрейлы:**
- Severity не определяется только LLM — есть таблица правил для очевидных случаев. LLM применяется только в неоднозначных
- Формулировка вопроса клиенту проходит через template-фильтр (никаких «извините за неудобства» от модели — фразы стандартизированы по тенанту)

### 4.3 UBO Tracing Agent

**Назначение.** Строит граф владения юрлицом и определяет конечных бенефициаров (УБО) — физлиц с долей контроля >25% по цепочке.

**Это самый сложный агент**, потому что:

- Учредители ООО могут быть юрлицами (не только физлицами), нужен рекурсивный спуск
- Иностранные юрлица в цепочке требуют загрузки документов клиентом и часто — апостиля
- Для АО владельцами выступают акционеры, и информация о них часто не в ЕГРЮЛ, а у регистратора (ВТБ Регистратор, Статус, НРК-РОСТ)
- Эффективная доля по цепочке считается перемножением долей на каждом уровне
- Контроль ≠ доля — для крупных АО с размытым владением УБО определяется через бенефициарный контроль (член СД, право вето и т.д.)

**Входы:**
```yaml
UBOTracingInput:
  legal_entity_inn: "7701234567"
  legal_entity_type: "LLC | JSC | NPF"
  egrul_data: {...}
  uploaded_documents: [...]   # доверенности, выписки от реестродержателей
  recursion_depth: 0
  max_recursion_depth: 5
```

**Выход:**
```yaml
UBOTracingOutput:
  graph: {
    nodes: [
      { id: "LE-7701", type: "LegalEntity", inn: "7701234567", name: "ООО Ромашка" },
      { id: "LE-7702", type: "LegalEntity", inn: "7702345678", name: "ООО Холдинг" },
      { id: "PE-1", type: "Person", full_name: "Иванов И.И.", citizenship: "RU" },
      { id: "PE-2", type: "Person", full_name: "Петров П.П.", citizenship: "RU" }
    ],
    edges: [
      { from: "LE-7702", to: "LE-7701", share: 0.60, type: "ownership" },
      { from: "PE-1", to: "LE-7701", share: 0.40, type: "ownership" },
      { from: "PE-1", to: "LE-7702", share: 0.50, type: "ownership" },
      { from: "PE-2", to: "LE-7702", share: 0.50, type: "ownership" }
    ]
  }
  ubos: [
    { 
      person_id: "PE-1", 
      effective_share: 0.70,    # 0.40 + 0.60*0.50
      control_basis: "ownership",
      paths: [["PE-1 → LE-7701 (40%)"], ["PE-1 → LE-7702 (50%) → LE-7701 (60%)"]]
    }
  ]
  unresolved_branches: [

      "node_id": "LE-FOREIGN-1",

    }
  ]
  status: "complete | partial | blocked"
```

**Модель.** Gemma 4 31B в thinking mode. Reasoning критичен — это многошаговая задача с рекурсией.

**Тулы:**
- `fetch_egrul(inn: str) → EgrulData` — выписка по ИНН
- `fetch_ao_shareholders(inn: str) → ShareholdersList` — запрос к регистраторам АО (если интеграция есть)
- `request_document_from_client(application_id: str, document_type: str, reason: str)` — отправка запроса клиенту через `notification-service`
- `compute_effective_share(paths: list[Path]) → float` — расчёт эффективной доли

**Логика агента (упрощённо):**

```python
def trace_ubo(legal_entity_inn, depth=0):
    if depth > MAX_DEPTH:
        return UnresolvedBranch(reason="max_depth_exceeded")
    
    egrul = fetch_egrul(legal_entity_inn)
    nodes, edges = [], []
    
    for founder in egrul.founders:
        if founder.is_person:
            nodes.append(person_node(founder))
            edges.append(ownership_edge(founder, legal_entity_inn, founder.share))
        elif founder.is_russian_legal_entity:
            sub_graph = trace_ubo(founder.inn, depth+1)  # рекурсия
            nodes.extend(sub_graph.nodes)
            edges.extend(sub_graph.edges)
            edges.append(ownership_edge(founder, legal_entity_inn, founder.share))
        elif founder.is_foreign_legal_entity:
            request_document_from_client(...)
            return UnresolvedBranch(reason="foreign_entity")
    
    return Graph(nodes, edges)

# После построения графа:
ubos = []
for person in graph.persons:
    paths = find_all_paths(person, root_legal_entity)
    effective_share = compute_effective_share(paths)
    if effective_share > 0.25:
        ubos.append(UBO(person, effective_share, paths))
```

LLM здесь нужен не столько для самой логики (она алгоритмическая), сколько для:
- Распознавания нестандартных формулировок в выписках («владельцем 100% долей является...»)
- Объяснения цепочек владения человеческим языком для комплаенс-офицера
- Обработки кейсов «контроль без доли» (договоры, право назначать ЕИО)

**Гардрейлы:**
- Проверка суммы долей: для каждого юрлица сумма всех `share` входящих edges должна быть ≈ 1.0 (с погрешностью на «казначейские» доли)
- Если граф слишком большой (>50 узлов) — автоматическая эскалация комплаенс-офицеру
- Никакой автоматики для иностранных юрлиц в цепочке — всегда ручной разбор

### 4.4 Risk Scoring Agent

**Назначение.** Считает риск-категорию клиента по политике 375-П и формулирует объяснение.

**Важно: основная модель здесь — НЕ LLM.** Скоринг делает CatBoost (или логистическая регрессия + правила) — потому что для аудита ЦБ нужна прозрачная объяснимость через SHAP-values, а LLM-скоринг это «чёрный ящик», который не пройдёт. LLM используется только для **формулирования объяснения** на естественном языке.

**Входы:**
```yaml
RiskScoringInput:
  legal_entity: {...}
  applicant: {...}
  ubo_graph: {...}
  screening_results: {
    "rosfinmon": { "matches": [], "checked_at": "..." },
    "fssp": { "active_proceedings_count": 0 },
    "arbitrage": { "as_defendant_count": 2, "total_amount": 500000 }
  }
  document_quality_signals: {...}
  tenant_policy: {...}    # пороги, веса, blocked OKVED, etc.
```

**Выход:**
```yaml
RiskScoringOutput:
  score: 0.34                 # 0..1
  category: "low | medium | high"
  factors: [
    { name: "company_age", value: "2 years", weight: -0.15, direction: "decreases_risk" },
    { name: "okved_main", value: "62.01", weight: -0.05, direction: "decreases_risk" },
    { name: "arbitrage_as_defendant", value: 2, weight: 0.10, direction: "increases_risk" },
    { name: "ubo_chain_depth", value: 1, weight: -0.08, direction: "decreases_risk" }
  ]
  explanation: "Клиент относится к низкой категории риска. Компания работает 2 года в IT-секторе, бенефициар — резидент РФ, прозрачная структура владения. Единственный фактор внимания — два арбитражных дела в качестве ответчика на сумму 500 тыс., однако объём не критичен и не относится к мошенническим спорам."
  recommendation: "auto_approve"
  triggered_review_rules: []   # правила, которые сработали жёстко
```

**Модели:**
- **Скоринг:** CatBoost, обучен на размеченных историях онбординга (изначально — синтетика, потом — реальные данные)
- **Объяснение:** Gemma 4 31B (или GigaChat для русского — оба тестируем)

**Тулы:**
- `compute_shap_values(model, features) → dict` — для feature importance
- `lookup_blocked_okved(code, tenant) → bool` — проверка по списку блокированных ОКВЭД тенанта
- `check_age(registration_date) → years`

**Гардрейлы:**
- **Hard-rules trump score** — если есть совпадение в перечнях Росфинмониторинга, итог автоматически `high` независимо от скора
- **Никакого автоматического `decline`** — только рекомендация
- Объяснение проходит факт-чекинг: каждое утверждение в нём должно быть в `factors` (не должно быть «галлюцинаций»)

**Метрики:**
- AUC-ROC модели на holdout
- Калибровка (predicted probability vs actual)
- % случаев, где `triggered_review_rules` не пуст
- Согласие с решением комплаенс-офицера (на средних/высоких рисках)

### 4.5 Conversational Agent

**Назначение.** Чат-помощник, который ведёт клиента через процесс онбординга, отвечает на вопросы, запрашивает документы, объясняет, что происходит.

**Это единственный агент, который напрямую разговаривает с клиентом.** Его границы должны быть особенно жёсткими.

**Входы:**
```yaml
ConversationalInput:
  user_message: "Я уже загрузил устав, что дальше?"
  conversation_history: [...]
  application_state: {...}      # read-only
  client_profile: {            
    "type": "applicant",        # либо applicant, либо authorized_signatory
    "legal_entity_type": "LLC"
  }
  tenant_config: {              # тон, стиль, тарифы банка
    "tone": "formal_friendly",
    "products": [...],
    "branch_locations": [...]
  }
```

**Выход:**
```yaml
ConversationalOutput:
  response_text: "..."
  suggested_actions: [          # для UI — кнопки/CTA
    { "type": "upload_document", "document_type": "protocol_director_appointment" }
  ]
  internal_state_update: {
    "should_escalate_to_human": false,
    "user_intent": "status_inquiry",
    "frustration_signal": "none"
  }
```

**Модель.** **T-pro / T-lite** или **Vikhr** (русскоязычные fine-tunes) — основные кандидаты. Для клиентского чата критична естественность русского, банковская терминология и тон. Качество выше, чем у мультиязычных Gemma/Qwen.

**Тулы (read-only + ограниченные write):**
- `read_application_state(app_id)` — только чтение, никаких изменений
- `request_document(type, reason)` — отправляет запрос документа клиенту, фиксируется в audit log
- `explain_required_documents(legal_entity_type)` — справочная информация
- `get_tariff_info(product_id)` — тарифы из конфига банка
- `escalate_to_human(reason)` — передаёт диалог оператору, ставит флаг

**Что агент НЕ может делать:**
- Одобрять или отклонять заявку
- Изменять тариф или продукт
- Давать обещания о сроках
- Обещать одобрение
- Раскрывать причины отказа (если они уже определены)
- Обсуждать другие приложения банка
- Давать налоговые / юридические консультации

**Гардрейлы:**
- **System prompt с жёсткими ограничениями** — что обсуждаем, что нет
- **Output filter** — пост-проверка ответа на запрещённые конструкции («гарантирую», «точно одобрят», «я уверен, что»)
- **Topic classifier** — отдельная маленькая модель, определяющая, on-topic ли вопрос. Off-topic → стандартный refuse
- **Frustration detector** — если клиент злится несколько раз подряд → автоматическая эскалация на человека
- **PII в исходящих** — модель не должна сообщать клиенту его собственные паспортные данные «обратно» (защита от соц. инженерии)

**Что агент проактивно делает:**
- При остановке клиента на каком-то шаге >24 часа — отправляет напоминание с конкретным следующим действием
- Если документ загружен с low confidence — объясняет, что нужен более качественный скан
- При появлении расхождения с ЕГРЮЛ — формулирует понятный вопрос (текст идёт от Reconciliation Agent, но Conversational обрамляет в стиль)

### 4.6 Compliance Assistant Agent (для оператора)

**Назначение.** Помощник для комплаенс-офицера банка, не для клиента. Сводит весь контекст по заявке в карточку с обоснованиями и рекомендацией. Отвечает на вопросы офицера типа «почему повысили риск?» или «что ещё проверить?».

**Зачем отдельный агент?** У клиента и комплаенса разные задачи. Клиенту — простой язык и подсказки. Офицеру — банковский жаргон, ссылки на нормативку, агрегация всех сигналов в одном месте.

**Входы:**
```yaml
ComplianceAssistantInput:
  application_id: "..."
  full_context: {...}     # всё, что собрали
  officer_question: "Почему этот клиент в средней категории?"  # опционально
```

**Выход:**
```yaml
ComplianceAssistantOutput:
  case_summary: "...",
  key_signals: [...],
  applicable_norms: [
    { "norm": "115-ФЗ ст. 7", "relevance": "..." }
  ],
  recommended_actions: [...]
  similar_past_cases: [...]   # из истории банка (через RAG)
```

**Модель.** Gemma 4 31B + RAG по корпусу нормативки (115-ФЗ, 375-П, 499-П, методички ЦБ).

**Тулы:**
- `search_past_cases(criteria)` — поиск похожих кейсов в истории банка
- `cite_norm(norm_id)` — точная цитата из нормативки
- `get_full_audit_trail(application_id)` — полный таймлайн заявки

## 5. Сценарии end-to-end

Покажу, как всё это работает вместе на трёх типичных сценариях.

### Сценарий 1. ИП через ЕСИА — полная автоматика

**Время от старта до открытия счёта: 3–7 минут.**

1. Заявитель входит через ЕСИА → identity-service получает паспорт, СНИЛС, ИНН
2. ext-egrip автоматически тянет выписку
3. **Document Intake Agent** не запускается (документы не нужны для ИП)
4. **Reconciliation Agent** не запускается (одно и то же данные)
5. **UBO Tracing Agent** не запускается (УБО = сам ИП)
6. ext-rosfinmon скрининг → match=0
7. **Risk Scoring Agent** считает скор, получает 0.18 → low
8. Зелёная зона → автоматическое одобрение
9. ABS Connector создаёт счёт через SAGA
10. **Conversational Agent** отправляет приветствие с реквизитами

Человек не участвует ни на одном шаге.

### Сценарий 2. ООО, низкий риск, единственный учредитель

**Время: 30–90 минут (включая загрузку документов клиентом).**

1. Директор входит через ЕСИА с полномочиями руководителя
2. ext-egrul тянет выписку
3. Клиент загружает: устав (PDF), решение единственного учредителя (PDF)
4. **Document Intake Agent** параллельно парсит оба документа → JSON
5. **Reconciliation Agent** сверяет с ЕГРЮЛ → 1 minor (форматирование адреса), не блокируем
6. **UBO Tracing Agent** строит граф из 2 узлов (юрлицо + физлицо), УБО = единственный учредитель = 100%
7. Скрининг → 0 совпадений
8. **Risk Scoring Agent** → 0.27 → low
9. Зелёная зона → авто-одобрение
10. Открытие счёта в АБС через SAGA

Человек не участвует.

### Сценарий 3. ООО, средний риск, цепочка владения с иностранным юрлицом

**Время: 2–5 рабочих дней.**

1. Директор входит, идентификация ОК
2. ext-egrul тянет выписку — учредители: ООО «Ромашка Холдинг» (60%), Иванов И.И. (40%)
3. Клиент загружает устав, протокол ОСУ
4. **Document Intake Agent** парсит документы
5. **Reconciliation Agent** — без расхождений
6. **UBO Tracing Agent** запускается, рекурсивно спускается:
   - ООО «Ромашка Холдинг» (ИНН 7702345678) → ext-egrul тянет выписку
   - У холдинга один учредитель — иностранное юрлицо «Romashka Cyprus Ltd»
   - Агент возвращает `unresolved_branches` → запрашивает у клиента легализованную выписку с апостилем
7. **Conversational Agent** отправляет клиенту понятное сообщение: «Для завершения проверки нам потребуется выписка из реестра компаний Кипра по Romashka Cyprus Ltd с апостилем. Срок предоставления — 14 дней».
8. Клиент через 3 дня загружает документ
9. **Document Intake Agent** парсит (есть multimodal-режим для иностранных документов, но точность ниже → automatic flag для ручной проверки)
10. **UBO Tracing Agent** дополняет граф, определяет конечного УБО — Иванов И.И. с эффективной долей 40% + 60%×100%×80% = 88%
11. **Risk Scoring Agent** → 0.52 → medium (повышается из-за иностранной структуры и ручной проверки документа)
12. **НЕ зелёная зона** → попадает в очередь к комплаенс-офицеру
13. **Compliance Assistant Agent** готовит для офицера сводку: граф владения, ссылки на 115-ФЗ ст.6, исторические похожие кейсы, рекомендация «approve with EDD»
14. Офицер кликает «одобрить с EDD»
15. ABS Connector создаёт счёт, но с риск-меткой `medium` — это влияет на лимиты в АБС

Человек участвует один раз — в финальном решении, но с уже подготовленным контекстом.

## 6. Обработка ошибок и fallback

Каждый агент может упасть. Стратегия обработки:

| Тип ошибки | Стратегия |
|---|---|
| LLM-вызов timeout | Retry 3 раза с exponential backoff |
| LLM возвращает невалидный JSON | Retry 2 раза с уточнением промпта, потом fallback |
| Модель недоступна (vLLM down) | Fallback на меньшую модель (32B → 7B) с флагом `degraded_mode` |
| Confidence извлечения < threshold | Эскалация на оператора, не блокируем воркфлоу |
| Tool-call ошибка (например, ЕГРЮЛ не отвечает) | Retry, потом пауза воркфлоу до восстановления |
| Адаптер АБС вернул ошибку | SAGA-компенсация, эскалация на DevOps |
| Все ретраи исчерпаны | Заявка помечается `manual_review_required`, оператор разбирает вручную |

**Принцип graceful degradation:** даже если ИИ-слой полностью недоступен, платформа не должна вставать. Воркфлоу должно уметь работать в режиме «всё на ручном разборе» — медленно, но корректно. Это конфигурируется через feature flags.

## 7. Human-in-the-loop: где и как

Места, где обязательно участие человека:

1. **Любое решение `decline` или `freeze`** — даже если агент рекомендовал
2. **Заявки в категории `medium` и `high`** — комплаенс-офицер делает финальное одобрение
3. **Расхождения с severity = `critical`** — офицер видит контекст, решает запросить документы или эскалировать
4. **Иностранные элементы в структуре владения** — всегда ручной разбор
5. **Документы с `confidence < 0.85`** — оператор перепроверяет извлечённые поля
6. **Эскалация от Conversational Agent** — оператор берёт диалог
7. **Срабатывание `red_flag` правил** — независимо от скора, идёт на разбор

UI комплаенс-офицера должен давать:
- Полный контекст заявки на одном экране
- Сводку от Compliance Assistant Agent
- Прозрачные обоснования всех ИИ-решений
- Кнопки: Approve / Approve with EDD / Request Document / Escalate / Decline (с обязательным комментарием)
- Ссылки на нормативку, релевантную решению

## 8. Continuous learning loop

Цикл улучшения агентов на основе реальной работы:

1. **Production sampling** — 1–5% запросов записываются (вход + выход модели)
2. **Officer feedback** — на каждое решение, которое было пересмотрено комплаенсом, фиксируется: что агент предлагал, что решил человек, причина расхождения
3. **Weekly review** — банковский эксперт + ML-инженер просматривают расхождения, добавляют интересные случаи в eval-корпус
4. **Eval regression** — обновлённый корпус тестирует кандидатов-моделей
5. **Promotion** — если новая модель показывает >5% улучшение на корпусе и не хуже на adversarial → переходит в shadow-mode, потом в production

Этот цикл работает только при наличии **выделенного банковского эксперта**, который отвечает за качество корпусов и разметки. Без него loop деградирует за 3–6 месяцев.

## 9. Метрики автоматизации

Что измеряем для оценки эффективности всего блока ИИ-автоматизации:

**Бизнес-метрики:**
- **Automation rate** — % заявок, прошедших полностью автоматически (целевое: ИП — 90%+, ООО — 50%+)
- **Time-to-account-reservation** — время от подачи заявки до резервного счёта (целевое: <5 мин для ИП)
- **Time-to-decision** — время от подачи до финального решения (auto или manual)
- **Officer time per case** — среднее время разбора заявки оператором (целевое: снижение на 60% против ручного процесса)

**Качественные метрики:**
- **False approval rate** — % одобренных заявок, где постфактум обнаружились нарушения (целевое: <0.1%)
- **False rejection rate** — % предложенных к отказу заявок, где после ручного разбора всё ОК (целевое: <5%)
- **Officer agreement rate** — на средних/высоких рисках, % решений комплаенса, совпавших с рекомендацией ИИ (целевое: 85%+)
- **Document parsing accuracy** — field-level F1 на eval-корпусе (целевое: >95% для ключевых полей)

**Операционные метрики:**
- **Per-application AI cost** — стоимость токенов на одну заявку (целевое: <50 рублей для ИП, <300 для ООО)
- **LLM latency p99** — на каждый агент
- **Model availability** — uptime каждой модели
- **Eval corpus drift** — насколько распределение production-запросов отличается от тестового корпуса

Все метрики — на дашборде, разрезы по тенанту, типу клиента, времени.

## 11. Что НЕ автоматизируем (намеренно)

Список того, что мы решили **не** автоматизировать ИИ-агентами, и почему:

- **Криптографические операции (УКЭП, ЭП)** — только проверенные библиотеки (КриптоПро, VipNet), без ИИ в цепочке
- **Создание счёта в АБС** — детерминированный SAGA-воркфлоу, без LLM-решений
- **Окончательное решение «отказать»** — только человек
- **Расчёт лимитов и комиссий** — конфигурация банка, не ИИ
- **Перевод документов** — для иностранных документов используем сервисы переводов с человеческой верификацией, не LLM
- **Юридические консультации клиенту** — Conversational Agent отказывается, направляет в банк
- **Скоринг сам по себе** — LLM не считает скор, только объясняет результат CatBoost (как уже описано)

Эти границы тоже нужно зафиксировать в ADR — как часть «AI policy» платформы.
