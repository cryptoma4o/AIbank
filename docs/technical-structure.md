# Техническая структура проекта

## White-label платформа онбординга юрлиц для российских банков

Документ описывает целевую архитектуру, технологический стек, структуру кодовой базы и план развёртывания платформы. Версия для команды разработки и архитектурных обсуждений.

---

## 1. Архитектурные принципы

Платформа строится на нескольких принципах, от которых нельзя отступать без сильного обоснования. Каждое из этих решений уже обсуждено и зафиксировано:

- **Multi-tenant by design.** Каждый банк — изолированный тенант. Изоляция на уровне схемы БД (schema-per-tenant), отдельных bucket-ов в объектном хранилище, отдельных топиков Kafka. Никаких `tenant_id` в общих таблицах.
- **Hybrid deployment.** Один и тот же артефакт разворачивается и в SaaS, и в контуре банка (on-prem). Никаких managed-сервисов AWS/GCP в коде — только то, что есть в любой среде: PostgreSQL, Kafka, Redis, MinIO.
- **Event-driven backbone.** Kafka как нервная система платформы. Все межсервисные взаимодействия через события + асинхронные команды. Синхронный RPC только там, где это критично для UX.
- **Configuration over code.** Бизнес-правила, риск-политики, формы, воркфлоу — конфигурация (YAML/JSON), а не код. Для нового банка не нужна разработка.
- **Domain-Driven Design.** Жёсткие границы bounded contexts: Onboarding, Risk, Documents, ABS Integration, AI. Каждый — отдельная команда / отдельный сервис / отдельная схема БД.
- **API-first, contract-driven.** Все API описаны в OpenAPI / gRPC proto до начала реализации. Контракты — источник правды.
- **Self-hosted LLM as default.** Модели крутятся в инфраструктуре (своей или банка), не за периметром.

## 3. Технологический стек

### 3.1 Языки

| Слой | Язык | Обоснование |
|---|---|---|
| Core services | **Go 1.22+** | Производительность, простой деплой, отличная stdlib для сетевых сервисов, любим банковским IT |
| ML / AI services | **Python 3.12** | Экосистема ML, vLLM, PyTorch |
| Frontend (web) | **TypeScript 5+** | Типобезопасность, общие модели с бэком |
| Адаптеры АБС (legacy) | **Java 21** | Если АБС-протокол требует SOAP/MQ-клиентов из мира Java |
| Скрипты, CLI | **Go / Python** | По месту |

### 3.2 Фреймворки

- **Backend (Go):** стандартная библиотека + chi (HTTP) + gRPC + sqlc (типизированный SQL) + temporal-go-sdk
- **Frontend:** Next.js 14 (App Router) + Tailwind CSS + shadcn/ui + TanStack Query
- **ML services:** FastAPI + vLLM + LangGraph (для оркестрации агентов)
- **Workflow:** **Temporal** — для SAGA-паттернов и длинных бизнес-процессов онбординга

### 3.3 Хранилища

| Назначение | Технология | Комментарий |
|---|---|---|
| Транзакционные данные | **PostgreSQL 16** | Schema-per-tenant, partitioning по дате |
| Кэш и сессии | **Redis 7** | С Redis Cluster для prod |
| Поиск и аналитика | **OpenSearch** | Замена Elastic с учётом лицензий |
| Документы и файлы | **MinIO** | S3-совместимое, on-prem friendly |
| Event store / streaming | **Apache Kafka** | KRaft mode (без ZooKeeper) |
| Vector DB для RAG | **Qdrant** | РФ-продукт, on-prem дружественный |
| Time-series метрики | **VictoriaMetrics** | Prometheus-совместимый, эффективнее по диску |

### 3.4 Инфраструктура

- **Оркестрация:** Kubernetes 1.30+ (везде — и SaaS, и on-prem)
- **Service mesh:** Istio (mTLS между сервисами, обязательно для аудита)
- **Ingress:** Nginx Ingress + cert-manager
- **Secrets:** HashiCorp Vault (с аудитом)
- **Identity / SSO:** Keycloak (поддержка SAML, OIDC, кастом-провайдеров для ЕСИА)
- **CI/CD:** GitLab CI (РФ-friendly) или Jenkins для on-prem

### 3.5 Observability

LGTM-стек, всё self-hosted:

- **Метрики:** VictoriaMetrics + Grafana
- **Логи:** Loki
- **Трассировка:** Tempo + OpenTelemetry SDK во всех сервисах
- **Алерты:** Alertmanager + интеграция с Telegram/Mattermost
- **Audit log:** отдельный immutable store на базе PostgreSQL с append-only таблицами и подписью записей

### 3.6 ИИ-инфраструктура

- **Inference engine:** vLLM (continuous batching, AWQ-квантизация); SGLang как альтернатива для structured output
- **Стратегия моделей:** **пул моделей с роутингом по типу задачи**, выбор финальных моделей — эмпирически по eval-harness (см. раздел 7.5)
- **Кандидаты на этапе оценки:**
  - **Gemma 4 31B / 26B-MoE** (Google DeepMind, Apache 2.0, multimodal-родословная Gemini 3, 256K контекст, native function calling) — основной кандидат для парсинга документов и reasoning
  - **Qwen 3.5 27B / 35B-MoE** (Alibaba, Apache 2.0, 201 язык, thinking mode) — основной кандидат для текстовых задач с русским
  - **T-pro / T-lite** (T-Tech) или **Vikhr** — русскоязычные fine-tunes для клиентского чата
  - **GigaChat / YandexGPT** через API — fallback для банков, не готовых к self-hosted
- **Эмбеддинги:** bge-m3 (хороший русский), альтернатива — E5-mistral; reranker — bge-reranker-v2-m3
- **GPU:** для SaaS — пул A100 / H100; для on-prem — то, что есть у банка (часто H20 / Ascend 910B)
- **Оркестрация агентов:** LangGraph
- **Prompt management:** собственный с версионированием в Git, A/B-тестирование через LLM Gateway
- **Eval framework:** собственный поверх pytest + ragas для RAG (см. раздел 7.5)

## 4. Сервисная архитектура по слоям

### 4.1 Edge Layer

**API Gateway** — единая точка входа, делает:

- Tenant routing по subdomain (`bank-name.platform.ru` → tenant ID)
- Rate limiting per tenant
- Проверка JWT и сертификатов
- Логирование всех запросов в audit log

**BFF (Backend-for-Frontend)** — отдельный для каждого приложения, агрегирует данные из микросервисов в формат, удобный UI. GraphQL.

### 4.2 Core Services

**`tenant-service`** — управление конфигурацией тенантов. CRUD, версионирование конфигов, валидация по JSON Schema. Источник правды для всех остальных сервисов.

**`identity-service`** — аутентификация клиентов (ИП / директор ООО) и сотрудников банка. Интеграция с ЕСИА (OIDC), УКЭП (КриптоПро SDK), вход по логин/паролю как fallback.

**`onboarding-orchestrator`** — Temporal-воркфлоу для каждой заявки. Состояния, переходы, компенсации. Один воркфлоу = одна заявка от начала до открытия счёта.

**`risk-engine`** — скоринг и правила. Внутри — `rule-engine` (декларативные правила) + ML-скоринг. Выдаёт скор и текстовое объяснение для комплаенс-офицера.

**`document-service`** — приём, хранение, версионирование, подписание документов. Поддержка ЭП по ГОСТ через КриптоПро / VipNet. OCR через ИИ-агента.

**`ubo-service`** — построение и хранение графа владения. Графовая модель в PostgreSQL (recursive CTE) или Neo4j для сложных АО.

**`client-service`** — единая карточка клиента (КУС). История всех событий, документов, решений.

### 4.3 Integration Layer

**`abs-connector`** — фасад над всеми адаптерами. Принимает команды в каноническом формате, маршрутизирует в нужный адаптер по тенанту, собирает события, гарантирует идемпотентность через дедуп-стор в Redis.

**`abs-adapter-*`** — отдельный микросервис на каждый АБС. Внутри — клиент к АБС (SOAP/proprietary/SFTP) + маппер каноническая модель ↔ модель АБС. Версионируется независимо.

**`ext-*`** — внешние интеграции, каждая отдельным сервисом для изоляции отказов:
- `ext-egrul` — ФНС, ЕГРЮЛ/ЕГРИП. Кэширование ответов на 24 часа.
- `ext-esia` — Госуслуги для бизнеса.
- `ext-rosfinmon` — перечни 115-ФЗ, обновление раз в сутки.
- `ext-fssp` — база ФССП (исполнительные производства). Используется Risk Scoring Agent при параллельном скрининге.
- `ext-spark` (опционально) — СПАРК или Контур.Фокус через API.

### 4.4 AI Layer

**`llm-gateway`** — единый прокси к LLM. OpenAI-совместимый API наружу, маршрутизация к разным backend-ам внутри (vLLM, GigaChat API, и т.д.). Делает:

- Маршрутизацию по типу задачи (короткий чат → 7B, парсинг устава → 32B)
- Подсчёт токенов и биллинг
- Гардрейлы на вход (PII-фильтр) и выход (запрет на «отказать клиенту»)
- Кэширование детерминированных запросов
- Логирование в audit log

**Агенты** — каждый отдельный сервис со своим API:

- `agent-document-intake` — multimodal-парсинг паспорта, устава, протоколов. На выходе — JSON.
- `agent-reconciliation` — сверка извлечённых данных с ЕГРЮЛ, формулирование вопросов клиенту.
- `agent-ubo-tracing` — рекурсивное построение графа владения по выпискам.
- `agent-risk-scoring` — фичи + объяснимый скор. Использует gradient boosting, не LLM.
- `agent-conversational` — клиентский чат-помощник на 7B-модели.

**`rag-service`** — RAG поверх корпуса банковской нормативки (115-ФЗ, 375-П, 499-П, методички ЦБ, типовые уставы). Используется агентами для ответов на регуляторные вопросы.

**`eval-harness`** — оффлайн-проверка качества агентов на размеченном корпусе. Запускается на каждый PR в `ai/`.

### 4.5 Поддерживающие сервисы

- `notification-service` — email/SMS/push, шаблоны на тенант
- `audit-service` — write-only API для audit log, чтение через отдельный read-сервис
- `billing-service` — биллинг банков по событиям (открытый счёт, проверка УБО и т.д.)

## 5. Доменная модель (каноническая)

Главные сущности, на которых строится всё. Хранятся в `packages/domain-model/`, генерируются для всех языков из единого источника.

```
Tenant (банк)
  └── Configuration (политики, правила, формы)

Application (заявка на онбординг)
  ├── Applicant (заявитель — физлицо)
  ├── LegalEntity (юрлицо — ИП / ООО / АО)
  ├── State (текущий статус, история переходов)
  ├── RiskAssessment (скор, факторы, решение)
  └── Decision (одобрено / отказ / на доработку)

LegalEntity
  ├── BasicInfo (ИНН, ОГРН, наименование, ОКВЭДы, адрес)
  ├── Officers (директор, бухгалтер, подписанты)
  ├── OwnershipGraph (для ООО/АО — граф владения)
  └── UBOs (бенефициары, выведенные из графа)

Document
  ├── Type (устав, протокол, паспорт, выписка...)
  ├── Source (загружен клиентом / получен из ЕГРЮЛ / etc)
  ├── Versions (история)
  └── Signatures (УКЭП, ПЭП, отметки)

Account (банковский счёт)
  ├── ReservedNumber (выданный сразу)
  ├── ABSAccountId (после создания в АБС)
  └── Status (резерв / активен / заблокирован)

AuditEvent (immutable)
  ├── Actor (кто — клиент, сотрудник, ИИ-агент)
  ├── Action
  ├── Subject
  └── Timestamp + Signature
```

Главное: **доменная модель — это контракт между всеми сервисами и UI**. Меняется только через ADR и согласование архитектора.

## 6. Универсальный ABS-коннектор

Самая сложная часть. Архитектура — Hexagonal + Anti-Corruption Layer.

```
[Core services] 
    ↓ (canonical commands)
[abs-connector] ← маршрутизация по тенанту
    ↓
[abs-adapter-cft / -diasoft / -rs-bank / mock]
    ↓ (proprietary API)
[АБС банка]
```

**Каноническая команда:**

```yaml
command: OpenAccount
idempotency_key: "uuid-of-application-step"
tenant: "bank-alpha"
payload:
  client_id: "..."
  account_type: "current_rub"
  signature_card_id: "..."
metadata:
  initiated_by: "agent-orchestrator"
  trace_id: "..."
```

**Каждый адаптер реализует:**
- `Translate(canonicalCommand) → ABSCommand`
- `Execute(ABSCommand) → ABSResponse`
- `MapResponse(ABSResponse) → CanonicalEvent`
- `IsIdempotent(idempotencyKey) → bool`

**Контрактные тесты** — для каждого адаптера набор golden-тестов с моком АБС. Регрессии ловятся в CI.

**SAGA через Temporal:** открытие счёта = воркфлоу с шагами `CreateClient → ReserveAccount → AttachSignatureCard → ActivateAccount`. На каждом шаге — компенсация.

## 7. ИИ-слой и LLM-инфраструктура

### 7.1 Топология inference

```
[агенты] → [llm-gateway] → [vLLM-pool / external API]
                ↓
        [audit-service] (логирование всех вызовов)
```

### 7.2 Стратегия моделей: пул, а не одна

Принципиальное решение: **не выбираем одну модель на платформу**. Вместо этого строим пул моделей-кандидатов и роутим запросы по типу задачи. Финальный выбор для каждой роли определяется эмпирически по eval-harness (раздел 7.5), а не по теоретическим бенчмаркам.

**Текущие кандидаты по подзадачам** (с указанием первого выбора жирным, обновляется по результатам eval):

| Подзадача | Кандидат №1 | Кандидат №2 | Что мерим |
|---|---|---|---|
| Парсинг документов (vision) | **Gemma 4 26B-MoE** | Qwen 3.5-VL 32B | Field-level F1 на сканах уставов и паспортов |
| Сверка с ЕГРЮЛ | **Gemma 4 31B** | Qwen 3.5 27B | Precision/recall на детекции расхождений |
| Граф УБО (reasoning) | **Gemma 4 31B** thinking mode | Qwen 3.5 27B thinking | Корректность графа на синт. кейсах |
| Чат с клиентом (RU) | **T-pro / Vikhr** | Qwen 3.5 7B | Качество русского + human preference |
| RAG-ответы по нормативке | **Gemma 4 26B-MoE** | Qwen 3.5 27B | Faithfulness, recall@5 |
| Скоринг риска | **CatBoost** (не LLM) | XGBoost + SHAP | Объяснимость для ЦБ |
| Эмбеддинги | **bge-m3** | E5-mistral | Recall@10 на банковской нормативке |

**Почему именно такой пул:**

- **Gemma 4** — multimodal-родословная Gemini 3 даёт сильный OCR и понимание сложно структурированных документов; 256K контекст позволяет загрузить устав целиком; Apache 2.0; native function calling. Слабая сторона — русский язык не в фокусе тренировки.
- **Qwen 3.5** — лучшее многоязычное покрытие (201 язык, 250K вокабуляр), зрелый thinking mode, больше размерных вариантов для тонкой настройки роутинга. Менее сильная multimodal-история.
- **Русскоязычные fine-tunes** (T-pro, Vikhr, Saiga) — для клиентского чата важен естественный русский, банковская терминология, тон. Mainstream-модели здесь часто звучат канцелярски.
- **CatBoost для скоринга** — не LLM, но критично: для ЦБ-аудита нужна объяснимость через SHAP-values. LLM-скоринг здесь архитектурно неверный выбор.

**Model Registry**

Внутренний реестр моделей с метаданными:
- Имя, версия, путь к весам / API endpoint
- Размер, требуемая VRAM, latency p50/p99
- Лицензия и ограничения коммерческого использования
- Поддерживаемые языки (с уровнями качества по eval)
- Результаты последней регрессии по всем задачам
- Стоимость токена (для биллинга тенанта)
- Статус: `experimental` / `candidate` / `production` / `deprecated`

**Агенты ссылаются не на конкретную модель, а на роль** (`agent.document-intake.model = "production-vision"`). Маппинг ролей на модели определяется конфигурацией тенанта. Это даёт три ценные вещи:

- Можно переключить модель без перевыкладки агента
- Разные банки могут использовать разные модели (один — Gemma, другой — Qwen, третий — GigaChat)
- A/B-тестирование новых моделей через изменение конфига, а не кода

### 7.3 Гардрейлы (обязательны)

- **Запрет на автономный отказ** — ИИ может рекомендовать `decline`, но финальное действие совершает человек.
- **PII-фильтр на входе** в LLM при SaaS-режиме — паспорта/ИНН не должны попадать в логи модели.
- **Версионирование промптов** — каждый промпт в Git, версия в логе вызова.
- **Журнал всех вызовов** — 5 лет хранения наряду с досье клиента.
- **Retry с деградацией** — если 32B недоступна, fallback на 7B + флаг для ручной перепроверки.

### 7.4 RAG-корпус

Хранится в Qdrant, обновляется по cron:
- 115-ФЗ + изменения
- Положения ЦБ 375-П, 499-П, 590-П
- Письма и методические рекомендации ЦБ
- Внутренние политики банка-тенанта (загружаются им самим)
- Типовые уставы и образцы документов

Чанкинг — по 500 токенов с overlap 100. Hybrid search (dense + sparse BM25).

### 7.5 Eval-harness и выбор моделей

Eval-harness — это инфраструктура объективной оценки моделей и агентов на корпусе банковских кейсов. Без неё выбор LLM превращается в субъективные обсуждения и vibes-checking, что недопустимо для системы, через которую проходят регуляторно-чувствительные решения.

**Архитектура:**

```
ai/eval-harness/
├── datasets/                      # Тестовые корпуса (версионируются как код)
│   ├── docs-parsing/              # Сканы паспортов, уставов + ground truth JSON
│   ├── reconciliation/            # Пары (документ, ЕГРЮЛ-выписка) + метки
│   ├── ubo-graphs/                # Структуры владения с эталонами
│   ├── ru-banking-chat/           # Q&A по банковским темам
│   ├── rag-quality/               # Вопросы по 115-ФЗ + источники
│   └── adversarial/               # Намеренно сложные/спорные кейсы
├── runners/                       # Запуск моделей через LLM Gateway
│   ├── batch_runner.py
│   ├── cost_tracker.py
│   └── parallel_executor.py
├── metrics/                       # Метрики по типам задач
│   ├── document_metrics.py        # Field-level F1, JSON validity
│   ├── graph_metrics.py           # Graph edit distance
│   ├── rag_metrics.py             # ragas: faithfulness, relevance
│   └── ru_quality.py              # russe-superglue + LLM-judge
├── reports/                       # Сохранение в PostgreSQL + Grafana
└── ci/                            # GitLab CI integration
```

**Тестовые корпуса — что и где брать:**

| Корпус | Содержание | Источник | Объём v1 | Кто размечает |
|---|---|---|---|---|
| docs-parsing | Сканы паспортов, уставов, протоколов + JSON | Синтетика + публичные образцы из ЕГРЮЛ | 200 кейсов | Внутренний разметчик + банк. эксперт |
| reconciliation | Пары документ ↔ ЕГРЮЛ с метками расхождений | Реальные ЕГРЮЛ-выписки | 500 кейсов | Банк. эксперт |
| ubo-graphs | Структуры владения 1–5 уровней | Синтетика по типовым шаблонам | 100 кейсов | Архитектор + банк. эксперт |
| ru-banking-chat | Вопросы клиентов и эталонные ответы | Размечены банк. экспертом | 300 пар | Банк. эксперт + продакт |
| rag-quality | Вопросы по нормативке + источник | 115-ФЗ, ЦБ-методички | 150 пар | Юрист по банк. праву |
| adversarial | Спорные кейсы, попытки jailbreak | Curated из боевых данных | 50 кейсов | Security + комплаенс |

Все корпуса хранятся в Git LFS, версионируются. Изменения в корпусе = PR с обоснованием. Это критично: если корпус «дрейфует», метрики теряют сравнимость во времени.

**Метрики по подзадачам:**

- **Парсинг документов** — field-level precision/recall/F1 по каждому полю отдельно (ИНН, ОГРН, наименование, директор, ОКВЭДы), JSON validity rate, latency p50/p99
- **Сверка с ЕГРЮЛ** — precision/recall на детекции расхождений, false positive rate (важно — каждый ложный алерт = дополнительный вопрос клиенту = ухудшение конверсии)
- **Граф УБО** — graph edit distance до эталона, точное совпадение списка УБО, корректность долей владения
- **Чат** — комбинация: ROUGE-L против эталона, RU-language quality (наша надстройка над russe-superglue), LLM-judge на парах ответов, в продакшене — DSAT (% жалоб на ответ)
- **RAG** — recall@5 (нашли ли релевантный документ), faithfulness через ragas (нет ли «галлюцинаций»), answer relevance, citation accuracy
- **Cross-cutting** — стоимость в рублях за кейс (важно для биллинга тенанта), latency, % отказов модели

**Запуск:**

- **На каждый PR в `ai/`** — fast subset (~50 кейсов на задачу), запуск ~5 минут, регрессия >5% блокирует merge
- **Еженедельная полная регрессия** — все корпуса, все модели-кандидаты, отчёт в Grafana
- **Pre-release gate** — обязательная полная регрессия перед выкатыванием новой версии агента или модели в production
- **Cost-aware ranking** — рейтинг моделей считается не только по метрике качества, но и по cost-per-correct-answer

**Production traffic sampling**

В продакшене 1–5% запросов записываются с входом и выходом для:
- Offline-разметки комплаенс-офицерами (был ли ответ корректен)
- Дообучения eval-корпусов на реальных кейсах
- Drift detection — алерт, если распределение запросов или метрик дрейфует относительно baseline

Очень важно: это **не replay** запросов на новой модели в продакшене, это **сэмпл логов для офлайн-анализа**. Различие принципиальное с точки зрения 152-ФЗ.

**Shadow mode для новых моделей**

Перед переключением на новую модель в production она работает в shadow-режиме: получает тот же запрос, что и production-модель, но её ответ только логируется и сравнивается с production-ответом. Неделя shadow-режима даёт сравнительные данные на реальном трафике без рисков для клиентов.

**Что критически важно зафиксировать заранее:**

- **Owner корпусов** — конкретный человек (банковский эксперт), который отвечает за качество разметки. Без него корпус превращается в мусор за полгода.
- **SLA на регрессию** — что считаем регрессией: падение F1 на 5%? на 1%? для какой задачи? Это нужно зафиксировать в ADR.
- **Versioned model snapshots** — сохраняем не только веса, но и точную версию vLLM, конфигурацию инференса, sampling-параметры. Без этого «модель X показала 89%» через год становится невоспроизводимой цифрой.

## 8. Безопасность и комплаенс

### 8.1 Изоляция тенантов

| Уровень | Механизм |
|---|---|
| База данных | Отдельная PostgreSQL schema на тенанта |
| Объектное хранилище | Отдельный bucket с IAM-политиками |
| Kafka | Отдельные топики с префиксом тенанта |
| Кэш | Префикс ключей `tenant:{id}:` + ACL |
| Логи | Лейблы Loki с tenant-id, фильтрация на чтение |
| LLM | Отдельный namespace в gateway, отдельный rate-limit |

### 8.2 Шифрование

- **В транзите:** TLS 1.3 везде, mTLS между сервисами через Istio
- **В покое:** PostgreSQL TDE + шифрование томов на уровне K8s storage class
- **Чувствительные поля:** дополнительное шифрование на уровне приложения через Vault Transit (ИНН клиента, паспортные данные)
- **Криптография по ГОСТ:** для УКЭП — КриптоПро CSP / VipNet CSP

### 8.3 Audit log

Append-only, immutable, с цифровой подписью каждой записи. Хранится 5 лет (требование 115-ФЗ). Структура:

```
{
  "timestamp": "...",
  "tenant_id": "...",
  "actor": {"type": "user|service|ai_agent", "id": "..."},
  "action": "decision.approved",
  "subject": {"type": "application", "id": "..."},
  "data": {...},
  "signature": "..."
}
```

### 8.4 Регуляторное соответствие

| Норма | Что закладываем |
|---|---|
| 115-ФЗ | KYC, скрининг по перечням, КУС, хранение 5 лет |
| 152-ФЗ | Согласия на ПДн, право на удаление, локализация в РФ |
| 375-П | Риск-категории клиентов, периодический пересмотр |
| 499-П | Идентификация, упрощённая идентификация |
| 187-ФЗ | КИИ — если банк-клиент относится к субъектам |
| ФСТЭК / ФСБ | Сертифицированные СКЗИ для УКЭП |
