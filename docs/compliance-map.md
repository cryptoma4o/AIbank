# Карта регуляторного соответствия

Документ связывает регуляторные требования российского законодательства с конкретными возможностями платформы. Используется на трёх этапах: проектирование (ничего не забыли), внедрение в банке (что показать ИБ-аудиту банка), периодический пересмотр (что изменилось в нормативке).

---

## 1. Регуляторный ландшафт

Платформа подпадает под несколько категорий регулирования:

| Категория | Применимые акты | Кто следит |
|---|---|---|
| Противодействие отмыванию (AML/CFT) | 115-ФЗ, 375-П, 499-П, 590-П | ЦБ РФ, Росфинмониторинг |
| Защита персональных данных | 152-ФЗ, 242-ФЗ (локализация) | Роскомнадзор |
| Информационная безопасность | 187-ФЗ (КИИ), приказы ФСТЭК | ФСТЭК России |
| Криптографические средства | ФЗ-63 (ЭП), приказы ФСБ | ФСБ России |
| Электронное взаимодействие | 149-ФЗ, 63-ФЗ | Минцифры |
| Регистрация ПО | Реестр отеч. ПО Минцифры | Минцифры |

Регулирование может пересекаться: например, при работе с УКЭП и хранении подписанных документов мы попадаем одновременно под 63-ФЗ, 152-ФЗ и 115-ФЗ.

## 2. 115-ФЗ — противодействие отмыванию

**Полное название:** ФЗ-115 «О противодействии легализации (отмыванию) доходов, полученных преступным путём, и финансированию терроризма».

**Базовое требование:** банк обязан идентифицировать клиента, оценивать его риск-категорию, скринить по перечням и хранить досье.

### Требования и реализация

| Требование 115-ФЗ | Где в платформе |
|---|---|
| Идентификация клиента (ст. 7) | `identity-service` (ЕСИА, УКЭП, паспорт) |
| Идентификация представителя | `identity-service` + проверка полномочий в Document Intake Agent |
| Идентификация бенефициарных владельцев | UBO Tracing Agent + ручной ввод для иностранных структур |
| Скрининг по перечню Росфинмониторинга | `ext-rosfinmon` сервис, обновление 1р/сутки |
| Скрининг по перечням ОЭСР | `ext-rosfinmon` (включён в общую схему) |
| Скрининг по перечню FATF | Дополнительный модуль (опционально для тенанта) |
| Категоризация по уровню риска (ст. 7.5) | `risk-engine` + Risk Scoring Agent |
| Упрощённая идентификация (ст. 7.2) | Отдельный воркфлоу для соответствующих сценариев |
| Запрет на установление отношений с анонимными лицами | Архитектурно: невозможно создать Application без идентификации |
| Хранение досье 5 лет (ст. 7) | Retention policy в `document-service` и `audit-service` |
| Уведомление в Росфинмониторинг (ст. 6) | Не наша зона; интерфейс для выгрузки в АБС банка |
| Внутренний контроль (ст. 7) | `audit-service` + дашборды для комплаенс-офицера |

**Артефакты для аудита ЦБ:**

- Полное досье клиента (выгрузка из `client-service`)
- Audit trail всех решений (`audit-service`)
- Отчёт о скрининге за период
- Лог обновлений перечней Росфинмониторинга

## 3. 375-П — Положение Банка России

**Полное название:** Положение Банка России от 02.03.2012 № 375-П «О требованиях к правилам внутреннего контроля кредитной организации в целях ПОД/ФТ».

### Ключевые требования и реализация

| Требование 375-П | Где в платформе |
|---|---|
| Программа идентификации | Workflow в `onboarding-orchestrator` |
| Программа управления риском (риск-категории) | `risk-engine` с категориями LOW/MEDIUM/HIGH |
| Программа выявления операций, подлежащих обязательному контролю | Не наша зона (это пост-онбординг) |
| Программа документального фиксирования | `audit-service` |
| Программа подготовки и обучения | Не наша зона; материалы для банка-тенанта |
| Периодический пересмотр риск-категории | Cron-job + триггеры в `risk-engine` |
| Обновление сведений о клиенте | Periodic re-screening, мониторинг изменений в ЕГРЮЛ |

**Периодичность пересмотра** (зашиваем в дефолтную конфигурацию тенанта):

- Низкий риск: раз в 3 года
- Средний: раз в год
- Высокий: раз в полгода

Конкретные сроки могут переопределяться банком через тенант-конфигурацию (см. `tenant-configuration.md`).

## 4. 499-П — упрощённая идентификация

**Полное название:** Положение Банка России 499-П «Об идентификации клиентов».

### Что важно

- Регулирует процедуру идентификации, в том числе **дистанционной** (через ЕСИА, ЕБС)
- Определяет случаи, когда возможна **упрощённая идентификация**
- Содержит требования к составу собираемых сведений

### Реализация

- `identity-service` поддерживает все каналы идентификации, предусмотренные 499-П: личное присутствие (через выезд курьера или офис), УКЭП, ЕСИА, ЕБС (опционально)
- Состав собираемых сведений зашит в `tenant-configuration` со ссылками на пункты 499-П
- Воркфлоу автоматически выбирает доступные методы идентификации в зависимости от типа клиента и риска

## 5. 152-ФЗ — персональные данные

**Полное название:** ФЗ-152 «О персональных данных».

### Базовые требования

| Требование | Реализация |
|---|---|
| Согласие субъекта на обработку (ст. 9) | Отдельный шаг в воркфлоу, согласие версионируется и хранится |
| Цели обработки заявлены | Текст согласия конфигурируется тенантом, шаблон от нас |
| Локализация ПДн в РФ (ст. 18) | Все продакшен-инстансы только в РФ-облаках или on-prem |
| Защита ПДн (ст. 19) | См. security-architecture.md |
| Право на удаление, на исправление | API клиентского кабинета + audit на каждое изменение |
| Уведомление об инцидентах в течение 24 часов | Incident response runbook |
| Категории ПДн | Чувствительные ПДн (паспорт, ИНН) — отдельное шифрование на уровне приложения |
| Уровень защищённости | УЗ-2 (минимально требуемый для банков) |

### Что должно быть готово на момент первой продажи

- Уведомление Роскомнадзора о начале обработки ПДн (как обработчик)
- Аттестат соответствия УЗ-2 (получается через лицензированную организацию)
- Перечень типовых форм согласий (в составе поставки)
- DPA-договор с банком (банк = оператор, мы = обработчик)

## 6. 590-П — кредитные истории

**Применимость:** косвенная. Если банк использует данные БКИ при онбординге.

### Реализация

- Платформа предоставляет интеграционный API для запроса в БКИ
- Запросы логируются в `audit-service` с указанием правового основания
- Согласие на запрос в БКИ — отдельный пункт в форме согласия клиента

---

## 7. 187-ФЗ — критическая информационная инфраструктура

**Применимость:** если банк-клиент относится к субъектам КИИ (а большинство банков относятся), то и наша платформа в его контуре становится частью КИИ.

### Что это меняет

- Для on-prem развёртывания нужно соответствие требованиям ФСТЭК по защите КИИ
- Платформа должна поддерживать категорирование объектов и взаимодействие с ГосСОПКА
- Использование исключительно отечественного ПО (см. реестр Минцифры)

### Реализация

- Все компоненты — open-source или отечественные (PostgreSQL, Kafka, Redis, OpenSearch, Keycloak — open-source; OS — Astra Linux / РЕД ОС в on-prem)
- Регистрация платформы в реестре отеч. ПО — обязательный артефакт первой версии
- Поддержка протоколов ГосСОПКА — отдельный модуль интеграции

---

## 8. 63-ФЗ — электронная подпись

**Применимость:** прямая. Платформа работает с УКЭП клиента и подписывает документы.

### Требования

- Использование сертифицированных СКЗИ (КриптоПро CSP, VipNet CSP)
- Проверка действительности сертификата в момент подписания
- Проверка отзыва (CRL/OCSP)
- Подпись по алгоритмам ГОСТ 34.10-2012 и ГОСТ 34.11-2012

### Реализация

- В document-service встроен криптомодуль с поддержкой КриптоПро / VipNet
- Каждая подпись сохраняется с детальной информацией: серийный номер сертификата, центр выдачи, статус на момент подписи
- Проверка цепочки доверия — обязательная часть валидации подписи

## 9. Сертификации и их сроки

| Сертификация | Срок получения | Стоимость (ориентир) | Кем выдаётся | Когда нужна |
|---|---|---|---|---|
| Аттестат УЗ-2 (152-ФЗ) | 3-4 месяца | 1.5-3 млн руб. | Лицензированный оператор | До первого пилота |
| Регистрация в реестре отеч. ПО | 2-3 месяца | До 100 тыс. руб. | Минцифры | До первой продажи |
| Лицензия ФСТЭК на разработку СЗИ | 4-6 месяцев | 2-4 млн руб. | ФСТЭК | До работы с КИИ |
| Лицензия ФСТЭК на ТЗКИ (если on-prem) | 4-6 месяцев | 2-4 млн руб. | ФСТЭК | Для on-prem |
| ISO 27001 | 6-9 месяцев | 3-5 млн руб. | Аккредитованный аудитор | Для крупных банков |
| Заключение ФСБ на криптомодули | Через КриптоПро/VipNet | Включено в лицензию | ФСБ (через вендора СКЗИ) | До работы с УКЭП |

**Логика последовательности:**

1. Сначала — реестр Минцифры (быстро, дешево, без него никто не разговаривает)
2. Параллельно — УЗ-2 (нужно для первого пилота)
3. После первого пилота — лицензии ФСТЭК (для on-prem-развёртываний)
4. Когда есть выручка — ISO 27001 (для крупных клиентов и экспорта)

## 10. Хранение и доступ к данным

### Сроки хранения (минимум)

| Тип данных | Срок | Основание |
|---|---|---|
| Досье клиента (документы, ПД) | 5 лет после прекращения отношений | 115-ФЗ ст. 7 |
| Audit log решений | 5 лет | 115-ФЗ + внутренние правила ЦБ |
| Логи доступа к ПДн | 3 года | Внутренние требования УЗ-2 |
| Системные логи | 1 год | Обычная практика |
| Метрики и аналитика | без ограничений (агрегаты) | По решению банка |

### Доступ к данным

- **Принцип минимальных привилегий** — каждый сотрудник банка имеет доступ только к той информации, которая нужна для его работы
- **Логирование всех доступов** — кто, когда, к какому досье
- **Запрос судов и правоохранительных органов** — отдельный воркфлоу, через юриста банка, всегда с записью основания

## 11. Регуляторные риски и их митигация

| Риск | Вероятность | Митигация |
|---|---|---|
| Изменение 115-ФЗ в части идентификации | Средняя (изменения регулярные) | Eнхаточная конфигурация воркфлоу, можем адаптировать без переработки кода |
| Запрет на использование иностранных моделей (LLM) | Средняя | Архитектура с self-hosted моделями + русскими fine-tunes |
| Ужесточение требований к локализации | Низкая | Уже всё в РФ |
| Введение ЕБС как обязательного канала | Средняя | Заложена интеграция с ЕБС как опция |
| Запрет на использование облачных решений в банках | Низкая | On-prem deployment поддерживается |
| Изменения в нормативке по УКЭП (новый ГОСТ) | Низкая | Через КриптоПро SDK обновляется автоматически |

## 12. Процесс мониторинга нормативных изменений

Без этого процесса compliance-map устареет за полгода. Закладываем:

- **Еженедельный обзор** изменений на сайтах: cbr.ru, minfin.gov.ru, rkn.gov.ru, fstec.ru, fsb.ru
- **Подписка** на обновления Гарант / КонсультантПлюс по применимым актам
- **Ежеквартальный регулятор-ревью** с банковским юристом (отслеживаем тенденции)
- **Полугодовой аудит** соответствия (внутренний или внешний)
- **При изменении нормативки** — обновление этой карты, при необходимости — ADR + изменения кода

**Owner процесса:** Юрист по банковскому праву + комплаенс-эксперт.
